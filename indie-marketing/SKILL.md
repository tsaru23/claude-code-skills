# indie-marketing

個人開発プロダクトの集客・マーケティングを、**設計 → 実行 → テスト記録 → 改善**の
サイクルで回すためのスキル。

前提となる思想(`references/playbook.md` に詳細):

- **マーケティングの本質はテスト。** 「この施策をやれば伸びる」という正解はなく、
  プロダクトのジャンル・ターゲットによって刺さる媒体が変わる。仮説を立てて小さく
  試し、数字を見て次を決める、これを繰り返すことしかない。
- **計測が無ければテストではない。** アクセス解析・登録数が見えない状態での発信は、
  何が効いたか後から復元できない。計測の確保は他のどの施策よりも先に置く。
- **有料は再現性、無料は時間。** お金を払えば短時間で再現性高く検証・集客できる。
  無料は時間がかかりバラつきが大きい。ステージに応じて使い分ける。
- **地道な作業が成果を出す。** 全自動でバズって収益化、という近道は基本的にない。
  この前提をユーザーに対して誤魔化さない。

## 手順

### 1. プロダクトと現状の棚卸し

以下を会話・コード・ストア情報などから把握する。分からないものはユーザーに聞く。
すべてを質問攻めにせず、**会話や成果物から読み取れるものは自分で埋めてから、
不明点だけをまとめて確認する**こと。

- **プロダクト**: 何を解決するツールか / 形態(iOS・Android・Webアプリ・CLI・
  ライブラリ等) / 課金モデル(無料・買い切り・サブスク・アフィリエイト等)
- **ターゲット**: 誰の、どんな場面の困りごとか。年齢層・使っているSNS
- **現状の数字**: ダウンロード数/ユーザー数、売上、レビュー数と評価、
  既存SNSアカウントのフォロワー数と属性
- **計測の有無**: アクセス解析は入っているか。流入数・登録数・実利用が数字で
  見えるか。**見えないなら、それが最初の施策になる**(手順4の施策0)
- **1人で価値が出るか**: 共有・複数人が前提のプロダクトかどうか。前提なら
  訴求の入口設計が変わる(`references/playbook.md`「マルチプレイヤー製品の落とし穴」)
- **これまでにやった集客**: 何を試して、結果どうだったか
- **使えるリソース**: 月にかけられる広告予算、週にかけられる時間

### 2. ステージ判定

棚卸しの結果から次のステージを判定し、ユーザーに提示して合意を取る。
ステージによって優先すべき施策が変わる(`references/playbook.md` の
「ステージ別の優先順位」を参照)。

| ステージ | 状態 | 最優先ですること |
|---|---|---|
| **S0 検証前** | まだ作っていない / 作りかけ | 広告で需要検証 + ウェイティングリスト獲得 |
| **S1 初期** | リリース済み、ユーザー0〜100 | 小額広告で初期ユーザー投入 + SNS運用の立ち上げ |
| **S2 成長** | ユーザー100〜1000、反応が出始めた | 共有機能・バイラルデザイン + 当たった訴求の横展開 |
| **S3 拡大** | 継続的に伸びている | SEO/LLMOメディアとASOの本格化、多言語・多チャネル化 |

**S0 の扱いは特に重要**: まだ作っていない・作りかけの段階なら、「作る前に広告で
需要を検証する」提案を必ず行う。作ってから需要がなかったと分かるのが最大の損失に
なるため。ただし最終判断はユーザーに委ねる。

### 3. チャネル選定

`references/channel-guide.md` を読み込み、プロダクトの特性に合うチャネルを選ぶ。
**すべてのチャネルを同時に始めない。** ステージに応じて2〜3本に絞る。

選定の考え方(詳細はガイド参照):

- 動きを見せないと魅力が伝わらないもの(ゲーム、アニメーション主体のUI)
  → TikTok / YouTube などの動画系
- 一画面で価値が伝わるもの(管理系・可視化系アプリ)→ X / Meta(Instagram・Threads)
- 検索意図が明確な課題を解決するもの → SEO/LLMOメディアの優先度が上がる
- 幅広い年齢層が対象 → SNS単独では届かない層があることを明示する

選定理由をユーザーに一言で説明すること(例:「可視化画面が主役なので静止画が強い
X/Meta を軸に、検索需要のある『サブスク 解約』系でSEOを裏で育てる」)。

### 4. マーケティング計画書の作成

`templates/marketing-plan.md` を読み込み、プレースホルダを埋めて
**作業ディレクトリに `marketing-plan-YYYYMMDD.md` として出力**する。

計画書には必ず次を含める。

- ステージ判定と根拠
- 選定チャネルと選定理由(不採用にしたチャネルとその理由も1行ずつ)。
  **チャネルは並列に並べず、供給元 → 展開先の関係で組む**(例: note 1本を
  X の3〜5ポストに割る)。週の稼働時間から逆算し2チャネルまでに絞る
- **施策0(計測の確保)**: 手順1で計測が無いと判明した場合、**必ず施策0として
  他のどの施策よりも先に置く**。計測済みならその旨を書いて省略する
- **今週やる施策**(施策0を除いて3つまで。多く並べない)
- 各施策の**仮説・実施内容・予算・成功基準の数値**
- 30日後に判断すること(続行 / 撤退 / ピボット)。集客指標だけでなく
  **「流入 → 登録」「登録 → 実利用」の転換率を必ず含める**

**成功基準は必ず数値で置く。** 「反応を見る」ではなく「CPA 300円以内で
ウェイティングリスト50件」のように書く。数値目安は `references/playbook.md` の
「数値の目安」を参照する。

### 5. 施策の実行支援

計画に沿って、ユーザーが求める施策の実行を支援する。各施策の具体的な進め方は
`references/playbook.md` と `references/channel-guide.md` に記載。

- **広告**: 訴求軸とクリエイティブ案(コピー・画像の構図)を複数提示する。
  画像生成が必要なら生成する。**広告アカウントでの入稿・課金操作はClaudeが
  代行しない**(注意事項を参照)。
- **SNS運用**: 日次ルーティンとターゲットアカウントの探し方を提示する。
  投稿文そのものの作成は **sns-post-writer スキル**に委譲する。
- **共有機能・バイラルデザイン**: 既存コードを読み、シェア導線の実装箇所と
  「スクショされる画面」の設計案を出す。実装を依頼されたらそのまま実装する。
- **SEO/LLMO**: 検索ワードから逆算した記事リストを作り、承認を得てから記事を
  生成する。1回の依頼で書く本数はユーザーと決める。
- **ASO**: ストアのスクリーンショット1〜2枚目の構成案、キーワード・カテゴリの
  見直し案を出す。

### 6. テストログの記録

施策を実行したら `templates/test-log.md` を読み込み、作業ディレクトリの
`marketing-test-log.md` に追記する(なければ新規作成)。既にログがある場合は
**新しい施策を提案する前に必ず読み込み**、過去に試して駄目だった施策を
繰り返し提案しないこと。

記録するのは: 日付 / チャネル / 仮説 / 実施内容 / コスト / 結果の数値 / CPA /
学び / 次アクション。

**失敗も必ず記録する。** 「反応がなかった」も検証結果であり、次の判断材料になる。

### 7. 振り返りと次サイクル

ユーザーから振り返りを求められたら、テストログを読み込んで以下を報告する。

- 成功基準に対する達成状況(数値で)
- CPAが基準内だったチャネル / 外れたチャネル(無料施策は「工数◯時間 / 獲得◯件」)
- **ファネルのどこで詰まっているかの切り分け**。流入 → 登録 → 実利用のどこで
  落ちているかで打つ手が正反対になる。**流入はあるのに登録されない / 登録は
  されるのに使われない場合、発信量を増やす提案をしてはならない。** LP または
  オンボーディングの改善に時間を移すよう提案する
  (`references/playbook.md`「数字が出ないとき、どこが壊れているかを切り分ける」)
- **当たった訴求の横展開先**(あるチャネルで反応が取れたクリエイティブ・切り口は
  他チャネルでも試す価値が高い)
- 次の30日の計画案

## 注意事項

- **実績・数字の虚偽表示は絶対にしない。** ストアのスクリーンショットや広告に
  載せる「ランキング1位」「◯万ダウンロード突破」などの社会的証明は、**実際に
  達成した事実のみ**を記載する。達成していない実績を提案してはならない。
  未達成なら、実際に出せる数字(現在のユーザー数、レビュー件数など)に置き換える。
- **広告の入稿・課金操作はClaudeが行わない。** クリエイティブ案・ターゲティング案・
  予算案の作成までを担当し、広告アカウントへのログイン、キャンペーンの作成・配信
  開始・決済は必ずユーザー自身が行う。予算額は必ずユーザーに確認する。
- **SNSへの実投稿は明示承認を必須とする。** 投稿は sns-post-writer スキルの手順
  (投稿直前に本文全文を提示して明示承認を得る)に従う。承認なしに投稿しない。
- **スパム的な運用を提案・実行しない。** 無差別な大量フォロー/アンフォロー、
  自動DM、複数アカウントによる自作自演、レビューの購入・依頼は各プラットフォームの
  規約違反であり提案しない。エンゲージメントはターゲットを絞った手動運用を基本とする。
- **1対1のやり取りが発生する場での全自動AI運用は勧めない。** リプライや
  コメント返信をAIに全任せするとパターンが露呈し、アカウントの信頼を損なう。
  一方、不特定多数に届ける動画・記事コンテンツのAI生成は有効な選択肢として扱う。
- **成果を保証しない。** 「これをやれば伸びます」と断定しない。すべては仮説と
  テストであり、数字が出なかった場合の撤退基準も同時に示す。
- 競合のコンテンツや広告クリエイティブを**コピー・改変流用しない**。参考にするのは
  構成・切り口のみ。
