## Cookie とストレージの分類

同意管理の設計は、まずCookie・ストレージ上のデータを用途別に4カテゴリへ分類することから始まる。

| カテゴリ | 用途の例 | 同意が必要か | 同意なしで使えるか |
|---|---|---|---|
| 必須(necessary) | ログインセッション維持、カート内容の保持、CSRF対策トークン、言語設定の一時保持 | 不要 | 使える（サービス提供に不可欠なため） |
| 機能(functional) | UIのテーマ設定記憶、直近の検索条件の保持、非必須のUX向上機能 | 地域による（EU/EEAでは原則必要） | 地域・実装による |
| 分析(analytics) | アクセス解析、ヒートマップ、A/Bテストの割り付け記録 | 地域による（EU/EEAでは原則必要、個人を特定しない集計のみの例外運用をとる事業者もある） | 匿名化・集計化の程度によるが、原則は同意前提で設計する |
| 広告(marketing) | 広告配信、リターゲティング、クロスサイトでのユーザー識別、コンバージョン計測用のCookie | 原則必要（多くの地域で） | 原則不可。同意取得後に発火させる |

判断の指針: 「必須」に分類できるのは、そのCookie・ストレージがないとユーザーが要求したサービス自体が提供できない場合に限る。マーケティング上便利、分析上有用、という理由だけでは「必須」に分類しない。

## Cookie以外の保存手段の比較

同意規律の対象は「Cookie」という技術要素そのものではなく、「端末への情報の保存・読み出し」という行為である。localStorageやIndexedDBを使っても、Cookieを使わない、という理由だけで同意取得義務を回避できるわけではない。

| 保存手段 | 永続性 | 容量目安 | JSからのアクセス可否 | XSS時のリスク | 同意要否の扱い |
|---|---|---|---|---|---|
| Cookie | 有効期限まで（セッションCookieはブラウザ終了まで） | 数KB程度 | 可（HttpOnly指定時は不可） | HttpOnly未指定なら窃取リスクあり | 用途に応じて必須〜広告まで分類（上表参照） |
| localStorage | 明示的に削除するまで永続 | 数MB程度（ブラウザ依存） | 可 | 窃取されると永続的に悪用されうる | Cookieと同様、用途で判断。トラッキング目的なら同意対象 |
| sessionStorage | タブを閉じるまで | 数MB程度（ブラウザ依存） | 可 | タブが開いている間はリスクあり | 用途で判断。セッション限定の機能保持なら必須扱いにできることが多い |
| IndexedDB | 明示的に削除するまで永続 | 大容量（数十MB〜、ブラウザ・端末依存） | 可（非同期API） | localStorageと同様のリスク | 用途で判断。大容量データのキャッシュ等、識別目的でなければ必須扱いにしやすい |
| サーバーサイドセッション | サーバー側の保持期間に依存 | サーバー側リソース次第で実質無制限 | 不可（クライアントはセッションIDのみ保持） | セッションID窃取（セッションハイジャック）のリスクに限定される | セッションID自体はCookie等で保持するため、そのCookieの分類に従う |

**原則**: 同意が必要かどうかは「Cookieかどうか」ではなく、「端末への情報の保存・読み出しに当たるか」「その情報が個人を識別・追跡する目的で使われるか」で決まる。localStorageやIndexedDBに識別子を書き込んでトラッキングに使う設計は、Cookieを使う場合と同様に同意管理の対象として扱う。

## 提供地域による分岐

Phase 1 Q5（提供地域）の回答に応じて、適用される規律の枠組みが変わる。

```
提供地域は?
├─ 日本国内のみ
│   ├─ 個人情報を第三者に提供するか（Cookie経由の識別子含む）
│   │   └─ Yes → 個人情報保護法上の「個人関連情報の第三者提供」の規律を確認する
│   │            （提供先で個人データとして取得されることが想定される場合、
│   │              本人同意の取得状況の確認等が必要になりうる）
│   └─ 利用者情報を外部の事業者に送信する仕組みがあるか（アクセス解析タグ、広告タグ等）
│       └─ Yes → 改正電気通信事業法の外部送信規律を確認する
│                （送信される情報の内容・送信先等を通知または公表する義務、
│                  および利用者に選択の機会＝オプトアウト等を提供することが
│                  求められる場面がある）
│
├─ EU/EEAを含む
│   └─ GDPR（データ保護）とePrivacy指令（Cookie等の端末アクセス）の双方を確認する
│       - 個人データの取り扱いは原則として法的根拠（同意、契約履行等）が必要
│       - Cookie等、必須以外の端末アクセスは事前の同意（オプトイン）が原則
│       - 同意取得前にデフォルトで有効化しない
│       - 「同意する」と「拒否する」を同程度の操作コストにする
│       - 同意取得の記録（いつ・何に・どう同意したか）を保存する
│
├─ 米国（カリフォルニア州等、州法がある地域）
│   └─ CPRA等のオプトアウト方式を確認する
│       - 「販売・共有」に該当する行為があるか（広告目的のデータ共有等）
│       - 該当する場合、"Do Not Sell or Share My Personal Information" 等の
│         オプトアウト手段を提供する
│       - オプトアウトはEUのような事前同意ではなく、事後に拒否できればよい設計
│
└─ 上記以外の地域を含む／グローバル展開
    └─ 対象地域ごとに規律が異なるため、Phase 1 Q4（運用体制）と照らして
       「最も厳しい地域の基準に統一する」か「地域判定で出し分ける」かを決める
```

上記を表に整理すると次のようになる。

| 地域 | 同意の方式 | バナーの必須要件の目安 | 記録保存 |
|---|---|---|---|
| 日本国内のみ | 通知・公表 ＋ オプトアウト機会の提供が中心 | 外部送信する情報の内容と送信先の通知・公表。同意バナー自体は法的必須ではないケースが多いが、任意設置は可 | 通知・公表の実施記録（いつ・どの内容を掲示したか） |
| EU/EEA含む | 事前同意（オプトイン）が原則 | 「同意する」「拒否する」を同等の操作性で提示。カテゴリ単位での選択を可能にする。同意前に非必須Cookieを発火させない | 同意取得の日時・内容・バージョンを記録し、事後に提示できるようにする |
| 米国カリフォルニア州等 | 事後オプトアウト | 「販売・共有」を行う場合はオプトアウトリンク（"Do Not Sell or Share"等）の設置 | オプトアウト意思表示の記録 |

いずれの地域も対象になりうる場合、最も厳格なEU/EEA基準（事前同意・オプトイン）で統一して設計すると、他地域の要件も概ね満たしやすい。ただし通知・公表義務など、事前同意方式だけではカバーしきれない個別の記載義務（外部送信規律の公表内容など）は、地域ごとに別途確認する。

## 同意管理（CMP）の設計要件

| 要件項目 | 設計のポイント |
|---|---|
| 同意カテゴリの粒度 | 「必須」「機能」「分析」「広告」の4分類を最低単位とする。カテゴリをさらに細分化する場合も、ユーザーが理解できる粒度に留める |
| 初回表示のタイミング | 初回訪問時、かつ非必須のCookie/ストレームが発火する前に表示する |
| 同意と拒否の操作コスト | 「すべて同意」ボタンと同じ視認性・クリック数で「すべて拒否」を選べるようにする。拒否だけ複数階層の奥に隠す設計は避ける |
| 設定変更の導線 | フッター等、常時アクセスできる場所に「Cookie設定」等のリンクを常設し、いつでも同意状態を変更できるようにする |
| 同意状態の保存期間 | 保存期間を定め（例: 6ヶ月〜1年）、期限が来たら再取得する。無期限に保存し続けない |
| 再取得のタイミング | プライバシーポリシーやCookie利用目的を変更した場合は、保存期間内であっても再度同意を取得する |
| 同意状態のバージョニング | 同意時のポリシーバージョンを記録し、ポリシー変更時に「どのバージョンへの同意か」を判別できるようにする |
| 同意前のタグ制御 | タグマネージャ等を使う場合、同意カテゴリごとにタグの発火条件を紐付け、同意が得られるまで対象タグをブロックする仕組みを組み込む |

## Google Consent Mode v2 の考え方

Googleの計測・広告タグ（GA4、Google広告等）向けの同意伝達の仕組み。4つのシグナルで同意状態を管理する。

| シグナル | 意味 |
|---|---|
| `ad_storage` | 広告関連のCookie/ストレージへの書き込みを許可するか |
| `analytics_storage` | アクセス解析関連のCookie/ストレージへの書き込みを許可するか |
| `ad_user_data` | ユーザーデータを広告目的で送信することを許可するか |
| `ad_personalization` | パーソナライズド広告（リターゲティング等）を許可するか |

基本的な流れは、ページ読み込み時にすべてのシグナルを `denied`（拒否）に初期化し、ユーザーが同意バナーで選択した内容に応じて `update` で状態を更新する、というものである。同意が得られていないシグナルについては、対応するタグが計測データを制限付きモードで送信する（Consent Mode非対応時のように完全に停止するわけではなく、モデリングを前提とした形で送信される場合がある点はGoogleの実装仕様に依存するため、導入時に公式ドキュメントで最新の挙動を確認する）。

実装イメージ（フレームワーク非依存の素のJS）:

```html
<!-- 計測タグの読み込みより前に、デフォルトをすべて denied に設定する -->
<script>
  window.dataLayer = window.dataLayer || [];
  function gtag(){ dataLayer.push(arguments); }

  gtag('consent', 'default', {
    'ad_storage': 'denied',
    'analytics_storage': 'denied',
    'ad_user_data': 'denied',
    'ad_personalization': 'denied',
    'wait_for_update': 500 // ミリ秒。CMPの表示・判定を待つ猶予
  });
</script>
```

```js
// 同意バナーでユーザーが選択を確定したタイミングで呼び出す
function onConsentDecision(choice) {
  // choice は { analytics: boolean, marketing: boolean } のような
  // アプリ側の同意状態オブジェクトを想定する
  gtag('consent', 'update', {
    'ad_storage': choice.marketing ? 'granted' : 'denied',
    'analytics_storage': choice.analytics ? 'granted' : 'denied',
    'ad_user_data': choice.marketing ? 'granted' : 'denied',
    'ad_personalization': choice.marketing ? 'granted' : 'denied'
  });

  // 同意状態と同意日時・ポリシーバージョンを永続化する
  localStorage.setItem('consentState', JSON.stringify({
    ...choice,
    consentedAt: new Date().toISOString(),
    policyVersion: 'v1'
  }));
}
```

`default` の呼び出しは計測タグ本体の読み込みより前に実行する必要がある。この順序を誤ると、同意前にタグが `granted` 前提で発火してしまう。

## 計測基盤の選択肢比較

| 選択肢 | 同意なしで使えるか | Cookieを使うか | データの所在 | コスト | 実装負荷 |
|---|---|---|---|---|---|
| GA4 | 原則不可（地域による） | 使う（クライアントID等） | Google側（地域設定によりデータ処理地域を選べる場合がある） | 標準機能は無料枠あり、高トラフィック時は上位プランを検討 | 中（タグマネージャ併用が一般的） |
| プライバシー重視の軽量アナリティクス（Plausible、Umami等） | 個人を識別しないCookieレス設計を謳う製品が多く、同意不要で運用できる場合が多い（製品ごとの実装を確認する） | 使わない製品が多い | セルフホストか、提供事業者のデータセンターかは製品による | セルフホストなら実質インフラ費用のみ、SaaS版は月額課金が一般的 | 低〜中（セルフホストはインフラ運用が発生） |
| 自前のイベント収集 | 収集項目次第（個人識別子を含めなければ同意不要にできる余地がある） | 設計次第（Cookie不使用も可能） | 自社インフラ内で完結させられる | インフラ費用＋開発工数 | 高（収集基盤・集計基盤を自前で構築する必要がある） |
| タグマネージャ経由（GTM等） | タグマネージャ自体は同意管理の実行基盤であり、配下のタグの性質に従う | 配下のタグ次第 | 配下のタグの提供元に従う | 無料枠のあるサービスが多い | 中（同意カテゴリとタグの紐付け設定が必要） |

「同意なしで使えるか」は各サービスの実装仕様とその時点の法解釈に依存するため、採用前に必ず提供事業者の公式ドキュメントで最新の扱いを確認する。

## 計測設計

計測基盤を選ぶ前に、何を計測するかを先に決める。

1. **North Star指標を1つ定める**（例: 「有料転換したユーザー数」「継続利用率」など、プロダクトの成功を最も代表する単一指標）
2. **補助指標を洗い出す**（North Star指標に至る過程を説明する指標。例: サインアップ数、初回アクション完了率、離脱率）
3. **イベント設計に落とし込む**（補助指標を計測するために必要なユーザー行動をイベントとして定義する）

### イベント命名規約

`object_action` 形式（対象_動作）などの一貫した規則を1つ選び、全体で統一する。

| 良い例 | 避けたい例 | 理由 |
|---|---|---|
| `signup_completed` | `SignUpDone`、`user-signed-up-event` | 大文字小文字・区切り文字が混在すると集計時の突合が壊れる |
| `cart_item_added` | `add_to_cart_click_button_v2` | バージョン番号や実装詳細をイベント名に含めない |
| `checkout_started` | `checkout` | 動詞（状態変化）を含めないとイベントの意味が曖昧になる |

### パラメータ設計と個人情報の扱い

- イベントのパラメータには、氏名・メールアドレス・電話番号等、個人を直接特定できる情報を載せない。
- ユーザーを追跡する必要がある場合は、ハッシュ化やランダムな内部IDなど、単体では個人を特定できない識別子を使う。
- 自由入力のテキスト（検索キーワード、フォーム入力内容など）をイベントパラメータにそのまま含めると、意図せず個人情報が計測基盤に流れ込むことがあるため、送信前に除外・マスキングの要否を検討する。

### UTMパラメータの運用

- `utm_source` / `utm_medium` / `utm_campaign` を最低限の3点セットとし、必要に応じて `utm_content`（広告文言の識別）、`utm_term`（検索キーワード）を追加する。
- 値の表記ゆれ（大文字小文字、スペース、日本語表記と英語表記の混在）を避けるため、命名規則を一覧化してチームで共有する。
- UTMパラメータはURLに残るため、個人情報や機微な情報を値に含めない。

### コンバージョン計測の設計

- コンバージョンの定義（何をもって「成果」とするか）をNorth Star指標・補助指標の設計と整合させる。
- 同一ユーザーの重複コンバージョンを防ぐため、一意なトランザクションID等で重複排除する仕組みを組み込む。
- 広告経由のコンバージョン計測は、同意が得られていないユーザーの行動を計測対象から除外する設計にする（Consent Modeのモデリング機能に頼る場合も、その前提を理解した上で採用する）。

## サーバーサイド計測とファーストパーティ化

### ブラウザ側計測の限界

- ブラウザのトラッキング防止機能（サードパーティCookieの制限・ITP等）や広告ブロッカーにより、クライアント側の計測タグが正しく発火しない、または送信がブロックされるケースが増えている。
- 計測データの欠損率が高くなると、意思決定の材料としての信頼性が下がる。

### サーバーサイド計測に寄せる場合の設計

- 自社ドメイン配下のエンドポイント（ファーストパーティ）を経由してイベントを収集し、サーバー側から計測基盤へ転送する構成にすると、ブラウザ側のブロック機構の影響を受けにくくなる。
- サーバーサイド計測に切り替えても、収集する情報が個人データに該当する場合や、広告目的で第三者に共有される場合は、引き続き同意取得の対象になる。「クライアント側の同意バナーを回避する手段」としてサーバーサイド計測を導入するのは規律の趣旨に反するため避ける。
- サーバー側でユーザーを識別するための情報（メールアドレスのハッシュ値等）を広告プラットフォームに送信する場合、その情報自体が個人関連情報の第三者提供に当たりうるため、Cookie経由の送信と同様の確認が必要になる。

## プライバシーポリシーに書くべき項目のチェックリスト

- [ ] 収集する情報の項目（氏名、メールアドレス、Cookie識別子、行動ログ等）
- [ ] 情報の利用目的（サービス提供、分析、マーケティング等、目的ごとに列挙）
- [ ] 第三者提供の有無と提供先（提供する場合は提供先の種類・提供する情報の範囲）
- [ ] 外部送信先の一覧（アクセス解析、広告配信、SNS埋め込み等の外部事業者名）
- [ ] 情報の保存期間（または削除の基準）
- [ ] 問い合わせ窓口（開示・訂正・削除等の請求を受け付ける連絡先）
- [ ] 使用しているCookie/ストレージの一覧（カテゴリ、名称、用途、保存期間）
- [ ] 同意の撤回・設定変更の方法への案内

## 実装チェックリスト

- [ ] Cookie/ストレージの利用箇所を棚卸しし、必須/機能/分析/広告の4カテゴリに分類した
- [ ] 提供地域を確認し、適用される規律（個人情報保護法・外部送信規律／GDPR・ePrivacy／CPRA等）を特定した
- [ ] 同意管理の方式（オプトイン／オプトアウト）を地域に応じて決定した
- [ ] 同意バナーで「同意する」と「拒否する」を同等の操作コストにした
- [ ] 同意取得前に非必須のタグ・スクリプトが発火しないよう制御した
- [ ] 同意状態の保存期間・バージョニング・再取得条件を設計した
- [ ] Consent Mode等、計測プラットフォーム側の同意連携を実装した（該当する場合）
- [ ] 計測するNorth Star指標・補助指標・イベント一覧を文書化した
