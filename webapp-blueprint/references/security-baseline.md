# セキュリティベースライン

Webアプリケーションの設計書にセキュリティ要件を転記するための参照資料である。散文の解説より
チェック可能な項目表を主体とする。AIはこの資料を読み、対象プロジェクトのデータ機微度レベルに
応じて該当する対策を設計書に転記し、レベルに満たない項目があれば🔴（要確認）として明示する。

## データ機微度レベル

以降のすべての対策項目に、次の3段階のいずれかで適用レベルを付ける。上位レベルは下位レベルの
対策を包含する（L3はL1・L2の対策をすべて含んだうえで追加対策を行う）。

| レベル | 定義 | 典型例 |
|---|---|---|
| L1 | 公開情報のみを扱う。個人を特定する情報の入力・保存がない | コーポレートサイト、問い合わせフォーム、公開LP |
| L2 | 個人情報を扱う。会員登録・ログイン機能がある | 会員制サービス、SaaSダッシュボード、予約システム |
| L3 | 決済情報・認証情報・要配慮個人情報（病歴、思想信条など）を扱う | ECの決済、医療系サービス、人事・給与システム |

L3に該当する場合は、対策の妥当性についてセキュリティ専門家・弁護士など専門家のレビューを
別途挟むことを設計書内で提案する。

## 「脆弱性ゼロ」の定義

脆弱性が存在しないことは証明できない。そのため設計書では「脆弱性ゼロ」を目標に掲げても
よいが、意味は次の3条件に置き換え、達成したか判定できる形で書く。3条件をすべて満たした
状態を「既知の脆弱性ゼロ」と呼び、これを公開の前提条件とする。

| # | 条件 | 判定方法 |
|---|---|---|
| 1 | 既知の脆弱性ゼロ: 依存パッケージの監査・静的解析（SAST）・シークレット検出で、重大度 High 以上の未対応の指摘が0件である | CI でこれらを毎回実行し、1件でもあればビルドを失敗させる |
| 2 | 放置ゼロ: 見つかった指摘（Medium 以下を含む）は、すべて「修正」か「受容」のどちらかに分類済みである。受容する場合は理由・影響範囲・見直し期限を記録する | 指摘一覧に未分類のものがない |
| 3 | 証拠のない ✅ ゼロ: チェックリストの ✅ には、確かめたコマンド・ツールの出力・本番の応答などの根拠が付いている | 根拠のない ✅ を ❌ として扱う |

- 重大度は、ツールが付けた値（CVSS 等）をそのまま使う。下げて扱う場合は条件2の「受容」として記録する。
- 新しく公開された脆弱性によって、公開後に条件1が崩れることがある。公開後も監査を定期実行し、
  対応期限（「脆弱性の受付と対応期限」の節）に沿って直す。
- 外部の診断（ペネトレーションテスト等）を受けても「ゼロ」の証明にはならない。L3 では
  上記3条件に加えて、専門家の診断を受けることを提案する。

## 多層防御の考え方

単一の対策だけに頼らず、複数の層で防御を重ねる（Defense in Depth）ことを基本方針とする。
たとえば入力バリデーションを通過した値であっても、出力時のエスケープ、データベース側の
制約、認可チェックといった別の層でも検証する。1つの層が突破されても他の層で被害を
食い止められる設計を目指す。

## OWASP Top 10（2025年版）対応表

2021年版からの主な変更: サプライチェーン（A03）と例外処理（A10）が独立した項目になり、
SSRF はアクセス制御（A01）に統合された。

| 項目 | リスク | Webアプリでの典型的な現れ方 | 実装レベルの対策 | 適用レベル |
|---|---|---|---|---|
| A01 アクセス制御の不備 | 権限のないユーザーが他人のデータや管理機能にアクセスできる。サーバーに内部資源へのリクエストを代行させられる（SSRF） | URL・IDを直接書き換えて他人のリソースを閲覧・更新できる（IDOR）、管理画面への認可チェック漏れ、BaaS の行レベル制御の設定漏れ、ログイン後の遷移先を外部 URL に差し替えられる（オープンリダイレクト）、ユーザー入力の URL をそのまま fetch する画像取得・Webhook 機能 | サーバー側で毎リクエスト認可判定を行う、オブジェクト単位の所有者チェックを徹底する、デフォルト拒否（許可リスト方式）にする、CORS の許可オリジンを必要最小限にする、遷移先は自サイト内の相対パスに限る。SSRF は「SSRF 対策」の節に従う | L1必須／L2必須／L3必須（SSRF は該当機能があれば必須） |
| A02 セキュリティ設定ミス | 既定値のまま・不要機能の放置による露出 | デバッグモードの本番残存、詳細エラーメッセージの露出、不要なポート・管理画面の公開、ストレージバケットの公開設定、セキュリティヘッダの未設定 | 本番ではデバッグ情報を非表示にする、環境ごとに設定を分離する、不要なミドルウェア・エンドポイントを無効化する、セキュリティヘッダを設定する、本番の応答ヘッダを外から確かめる | L1必須／L2必須／L3必須 |
| A03 ソフトウェアサプライチェーンの失敗 | 依存パッケージ・ビルド環境・配布経路を経由した脆弱性や悪意あるコードの混入 | 既知の脆弱性を持つ npm パッケージ、乗っ取られたパッケージの新しい版を自動で取り込む、`postinstall` で認証情報を盗むパッケージ、版を固定していない GitHub Actions、EOL のランタイム | 「依存関係とサプライチェーンの管理」の節に従う | L1必須／L2必須／L3必須 |
| A04 暗号化の失敗 | 通信・保存データの盗聴や漏洩 | 全体HTTPS化の漏れ、パスワードの平文・弱いハッシュでの保存、機微データの無暗号化保存 | 全ページHTTPS化とHSTS、パスワードはbcrypt/argon2でハッシュ化、決済・認証情報など機微データは保存時も暗号化、TLS設定は最新の推奨構成に従う、乱数は暗号論的に安全な生成器（`crypto.getRandomValues` 等）を使う | L1必須（HTTPS）／L2必須／L3必須 |
| A05 インジェクション | SQL・NoSQL・OSコマンド・HTML 等への不正な入力混入 | 文字列結合によるSQL生成、テンプレートへの未エスケープ埋め込み（XSS）、シェルコマンドへのユーザー入力混入、LLM へのプロンプトインジェクション | ORM・プレースホルダ（パラメータ化クエリ）を必ず使う、シェル実行を避けるか引数配列で渡す、スキーマ駆動バリデーションを境界で通す、XSS は「XSS対策」の節に従う | L1必須／L2必須／L3必須 |
| A06 安全でない設計 | 実装以前の設計段階での欠陥（脅威モデリング不足） | パスワードリセットの推測可能なトークン、ビジネスロジックの悪用（数量に負数を渡す等） | 設計段階で脅威モデリングを行う、限界値・異常系の業務ロジックを洗い出す、外部決済・認証基盤など実績のある部品に委譲する | L1推奨／L2必須／L3必須 |
| A07 認証の失敗 | ログイン・セッション管理の不備 | ブルートフォース対策なし、セッション固定攻撃、弱いパスワードポリシー | レート制限、多要素認証（L3）、セッションIDの認証後再発行、安全なCookie属性 | L1必須（該当機能があれば）／L2必須／L3必須 |
| A08 ソフトウェアとデータの整合性の不具合 | 検証なしの更新・データ受け入れによる改ざん混入 | 署名検証なしの Webhook 受信、信頼できないソースからのデシリアライズ、CDN から読み込むスクリプトの改ざん | Webhook の署名検証（未設定時は拒否する）、デシリアライズ対象の型制限、外部 CDN のスクリプトには SRI（`integrity` 属性）を付ける | L1推奨／L2必須／L3必須 |
| A09 ログとアラートの失敗 | 侵害の検知・追跡ができない | ログ未記録、ログはあるが誰も見ていない、異常があっても通知が飛ばない | 認証・認可の失敗と重要操作を記録する、アラート閾値と通知先を設定する、ログを改ざん困難な形で保存する | L1推奨／L2必須／L3必須 |
| A10 例外条件の不適切な処理 | エラーや想定外の状態で、安全でない側に倒れる | 外部サービスの障害時に認可チェックを飛ばして処理を続ける、例外メッセージやスタックトレースを利用者に返す、途中で失敗した処理が中途半端な状態で残る | 「エラー処理（閉じる側に倒す）」の節に従う | L1必須／L2必須／L3必須 |

## 入力バリデーション

**原則: クライアント側の検証はUXのためであり、サーバー側の検証が本体である。** クライアント側
検証は開発者ツールやAPI直叩きで容易に迂回できるため、セキュリティ上の防御としては機能しない。

- スキーマ駆動バリデーション（zod、Yup、Valibot等）を用い、外部入力が信頼境界を越える箇所で
  1回だけ厳格に検証する。検証を通過したデータのみを内部で扱う。
- 検証は「型」「長さ」「形式」「値域」「許可される文字集合」の観点で行う。
- ホワイトリスト方式（許可する値を列挙）を優先し、ブラックリスト方式（禁止する値を列挙）に
  頼らない。

信頼境界の図（テキスト）:

```
[ブラウザ/外部クライアント]  … 信頼できない
        │  (a) UIレベルの簡易検証（UX向上のため。防御としては無効）
        ▼
──────────── 信頼境界 ────────────
        │  (b) サーバー入力口でのスキーマ検証（ここが本体。1箇所に集約する）
        ▼
[アプリケーション内部]        … 検証済みデータのみが流通する
        │
        ▼
[DB / 外部API / ファイルシステム]
```

- [ ] 外部入力（フォーム、クエリパラメータ、APIリクエストボディ、ファイル、ヘッダ）はすべて
      サーバー側でスキーマ検証している
- [ ] クライアント側検証はサーバー側検証の代替として扱っていない
- [ ] 検証エラー時のレスポンスに内部実装の詳細を含めていない

スキーマ駆動バリデーションのイメージ（zod相当の擬似コード）:

```
const CreateUserInput = schema.object({
  email: schema.string().email().max(254),
  displayName: schema.string().min(1).max(50),
  age: schema.number().int().min(0).max(150).optional(),
});

// APIの入り口で1回だけ検証し、以降は検証済みの型として扱う
const input = CreateUserInput.parse(requestBody);
```

## 認証の実装指針

| 項目 | 指針 | 適用レベル |
|---|---|---|
| パスワードのハッシュ化 | bcryptまたはargon2を使う。平文保存、MD5、SHA1（ソルトなし単純ハッシュ）は禁止する | L2必須／L3必須 |
| パスワードポリシー | 長さ（12文字以上を目安）を優先し、記号・大文字必須などの複雑さ要件を過度に押し付けない。既知の漏洩パスワードリストとの照合を検討する | L2必須／L3必須 |
| ログイン試行のレート制限 | IPアドレス単位・アカウント単位の双方で試行回数を制限し、一定回数失敗で一時ロックまたは遅延を入れる | L2必須／L3必須 |
| アカウント列挙の防止 | 「メールアドレスが存在しません」等、存在有無を判別できるメッセージ・応答速度差を避け、成功/失敗で同一の応答にする | L2推奨／L3必須 |
| 多要素認証（MFA） | TOTPアプリ等による2段階目の認証を提供する。決済・認証情報を扱う場合は必須とする | L2推奨／L3必須 |
| パスワードリセットのトークン設計 | トークンは十分なランダム性を持ち、有効期限（目安: 数十分〜1時間程度）を設け、使用後は即失効させる単回使用とする | L2必須／L3必須 |
| セッション固定攻撃の防止 | ログイン成功時に必ずセッションIDを再発行する（ログイン前のセッションIDを使い回さない） | L2必須／L3必須 |
| 外部 ID 連携（OAuth / OIDC） | 認可コードフローに `state` と PKCE（S256）を必ず付け、`state` は署名付き・短命の cookie と突き合わせる。id_token は `aud`（自分のクライアント ID）・`iss`・`exp`・`email_verified` を検証する。利用者の識別には変わらない `sub` を使い、メールアドレスを主キーにしない。`sub` には一意制約を付ける | L2必須／L3必須 |
| パスワードから外部 ID 連携への移行 | 既存のパスワードアカウントは一度だけパスワードでログインさせ、連携を済ませたらパスワードのハッシュを消す。連携済みアカウントへのパスワードログインは、存在を悟らせない同一の失敗応答で拒否する | L2推奨／L3必須 |

## 認可の実装指針

**原則: 認可はサーバー側（または DB 側）で、デフォルト拒否で行う。** 画面上でボタンを
隠すのは UX であり、防御ではない。

- [ ] すべての API・Server Action・ルートハンドラで、ログイン状態に加えて「その利用者がその
      リソースを操作してよいか」（所有者・所属組織・ロール）を確かめている
- [ ] リソースの取得は「ID だけ」でなく「ID と所有者」の条件で行う（例: `WHERE id = ? AND owner_id = ?`）
- [ ] 管理機能は一般利用者と別の認可判定を通し、URL を知っているだけでは開けない
- [ ] 認可のテストとして、利用者 A のトークンで利用者 B のリソースを読む・書く・消すリクエストを
      送り、すべて拒否されることを自動テストで確かめている

### BaaS（Supabase / Firebase）を使う場合

BaaS ではブラウザから DB を直接読み書きするため、DB 側の規則が唯一の認可になる。
規則の書き忘れが、そのまま全件漏洩につながる。

| 項目 | 指針 | 適用レベル |
|---|---|---|
| 行レベルの制御を全テーブルで有効にする | Supabase は外部から見えるスキーマの全テーブルで RLS（Row Level Security）を有効にし、ポリシーで `auth.uid()` と所有者列を突き合わせる。RLS を有効にしてポリシーを書かない状態は全拒否になるため、必要な操作（select / insert / update / delete）ごとにポリシーを書く | L1必須（DB を使う場合）／L2必須／L3必須 |
| Firebase の規則 | Firestore・Storage の Security Rules を `allow read, write: if false;` を起点に書き、`request.auth.uid` で所有者を確かめる。テスト用の「全許可」規則を本番に残さない | L1必須（DB を使う場合）／L2必須／L3必須 |
| 鍵の使い分け | クライアントに渡してよいのは公開用の鍵（Supabase の anon / publishable key、Firebase の Web 設定）だけである。RLS を無視できる鍵（Supabase の service_role / secret key、Firebase Admin SDK の認証情報）はサーバー専用にし、クライアントのバンドルに含めない | L1必須／L2必須／L3必須 |
| ストレージ | バケットごとに公開・非公開を決め、非公開バケットにもポリシーを書く。利用者のファイルはパスに利用者 ID を含め、ポリシーでそれを確かめる | L2必須／L3必須 |
| 規則の検証 | 他人のトークン・未ログインの状態で読み書きを試すテストを書く（Firebase はエミュレータ、Supabase はローカル環境で実行できる）。Supabase はダッシュボードのセキュリティ指摘（Security Advisor）が0件であることを公開前に確かめる | L2必須／L3必須 |
| DB 関数 | `security definer` の関数は RLS を迂回する。使う場合は関数内で呼び出し元の権限を確かめ、`search_path` を固定する | L2必須（該当機能があれば）／L3必須 |

## セッション/Cookieの属性

| 属性 | 指針 |
|---|---|
| `HttpOnly` | セッションCookieには必ず付与し、JavaScriptからの読み取りを防ぐ |
| `Secure` | HTTPS通信でのみ送信されるよう必ず付与する |
| `SameSite` | 用途に応じて`Lax`/`Strict`/`None`を使い分ける（下表参照） |
| `Path` | Cookieが必要なパスに限定し、不要に広いスコープを避ける |
| `Max-Age` | セッションの性質に応じて妥当な有効期限を設定する。機微度が高いほど短めにする |

`SameSite`の使い分け:

| 値 | 挙動 | 使いどころ |
|---|---|---|
| `Strict` | 自サイト内の遷移のみCookieを送信する | 銀行取引など、外部からの遷移でログイン状態を維持する必要がない機微な操作 |
| `Lax` | 通常のリンク遷移（トップレベルGET）ではCookieを送信するが、クロスサイトのPOST等では送信しない | 一般的なログインセッションCookieの既定値として妥当 |
| `None` | クロスサイトでも常にCookieを送信する。`Secure`との併用が必須 | サードパーティ埋め込み（決済ウィジェット等）でクロスサイトCookieが必要な場合のみ |

## CSRF対策

- `SameSite=Lax`または`Strict`のCookieのみで足りるケース: 状態変更を伴うエンドポイントが
  すべて対応ブラウザ経由のCookie認証で完結し、サードパーティからのクロスサイトPOSTを許容する
  必要がない場合。
- トークン方式が別途必要なケース: 古いブラウザ・アプリ内WebViewなど`SameSite`が効かない
  環境への対応が必要な場合、決済など特に重要な操作で多層防御を行いたい場合。

| 方式 | 概要 | 特徴 |
|---|---|---|
| Double Submit Cookie | Cookieとリクエストボディ/ヘッダの両方にトークンを載せ、サーバーで一致を検証する | サーバー側にトークンの保存が不要で実装が比較的簡単。Cookie自体の窃取には弱い |
| Synchronizer Token | サーバー側でセッションに紐づくトークンを発行し、フォーム送信時に照合する | セッション管理と統合され安全性が高いが、サーバー側に状態を持つ必要がある |

## XSS対策

- [ ] フレームワークのデフォルトの自動エスケープ機構に乗り、独自の文字列結合でHTMLを組み立てない
- [ ] `dangerouslySetInnerHTML`（React）、`v-html`（Vue）、`innerHTML`の直接操作を使う場合は、
      DOMPurify等のサニタイズライブラリを必ず通す
- [ ] ユーザー入力由来のURLを`href`/`src`に埋め込む際は、スキームを検証し`javascript:`等の
      実行可能スキームを排除する
- [ ] リッチテキスト入力を受け付ける場合は、許可するタグ・属性のホワイトリストを定義する

## セキュリティヘッダ

| ヘッダ | 推奨値の方向性 |
|---|---|
| `Content-Security-Policy` | nonceまたはhashベースでスクリプト実行元を制限する。`unsafe-inline`は避ける。既存サイトへの導入時は`Content-Security-Policy-Report-Only`で違反状況を観測してから本適用に切り替える段階導入を行う |
| `Strict-Transport-Security` | `max-age`を長期（目安: 半年〜1年相当の秒数）に設定し、サブドメインを含める場合は`includeSubDomains`を付与する |
| `X-Content-Type-Options` | `nosniff`を設定し、MIMEタイプスニッフィングによる誤解釈を防ぐ |
| `Referrer-Policy` | `strict-origin-when-cross-origin`等、外部への遷移時にフルURLを漏らさない設定にする |
| `Permissions-Policy` | カメラ・マイク・位置情報など、実際に使用しない機能を明示的に無効化する |
| `X-Frame-Options` / `frame-ancestors` | 自サイトを他サイトのiframeに埋め込ませない場合は`DENY`または`frame-ancestors 'none'`を設定する。CSPの`frame-ancestors`が優先されるため両方設定する場合は矛盾がないようにする |

CSP構築の指針:

- インラインスクリプト・スタイルは可能な限り外部ファイル化する。
- やむを得ずインラインが必要な場合はリクエストごとに生成したnonceをスクリプトタグとヘッダの
  両方に付与するか、内容が固定であればhashベースで許可する。
- サードパーティスクリプト（解析タグ等）を許可するドメインは必要最小限に絞る。

nonceベースのCSPヘッダ値のイメージ:

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-<リクエストごとに生成したランダム値>';
  style-src 'self' 'nonce-<同上>';
  img-src 'self' data:;
  connect-src 'self';
  frame-ancestors 'none';
```

段階導入時は、まず`Content-Security-Policy-Report-Only`で同等のポリシーを配信し、
違反レポートの送信先（`report-to`/`report-uri`）を設定して既存ページへの影響を観測してから、
問題がないことを確認したうえで本適用（`Content-Security-Policy`）に切り替える。

## ファイルアップロード

- [ ] 拡張子ではなくファイルの実際の内容（マジックバイト等）でファイル種別を判定する
- [ ] アップロードサイズの上限を設定する
- [ ] アップロードされたファイルは実行権限のない領域（Webサーバーが直接実行しないパス・
      ストレージサービス等）に保存する
- [ ] 配信時は`Content-Disposition: attachment`の付与や、アプリケーション本体とは別オリジンでの
      配信を検討し、アップロードファイル経由のXSS実行を防ぐ
- [ ] 画像アップロードは再エンコード（サムネイル生成等の過程でのデコード・再エンコード）を行い、
      ファイルに埋め込まれた不正なペイロードを排除する

## CORS

- [ ] 同一オリジンで完結する構成なら、CORS ヘッダを返さない（許可しないのが既定値）
- [ ] 別オリジンから呼ばせる場合は、許可するオリジンを完全一致の許可リストで指定する。
      リクエストの `Origin` をそのまま `Access-Control-Allow-Origin` に返さない
- [ ] `Access-Control-Allow-Credentials: true` と `Access-Control-Allow-Origin: *` を組み合わせない
      （ブラウザが拒否するため、`Origin` の反射で回避しようとする実装が生まれやすい）
- [ ] 許可するメソッド・ヘッダも必要なものだけに絞る

## オープンリダイレクト

ログイン後の戻り先（`?next=` `?redirect_to=` 等）や OAuth のコールバックで、利用者が指定した
URL へそのまま遷移させると、正規ドメインを経由したフィッシングに使われる。

- [ ] 戻り先は `/` で始まる自サイト内の相対パスだけを受け付ける。`//evil.example` のような
      プロトコル相対 URL と `\` を含むものは拒否する
- [ ] 外部への遷移が必要な場合は、遷移先を許可リストで持ち、パラメータには URL ではなく
      許可リストのキーを渡す
- [ ] OAuth のリダイレクト URI は、認証基盤側に完全一致で登録する（ワイルドカードを使わない）

## SSRF 対策

サーバーが利用者の指定した URL を取りに行く機能（画像の取り込み、OGP 取得、Webhook の
送信先登録等）がある場合に適用する（L2必須／L3必須）。

- [ ] 取得先のホストを許可リストで制限できるなら、そうする
- [ ] 許可リストにできない場合は、名前解決後の IP アドレスがプライベート・ループバック・
      リンクローカル（`169.254.169.254` のクラウドメタデータを含む）でないことを確かめる。
      確かめた IP に対して接続し、名前解決をやり直さない（DNS リバインディング対策）
- [ ] リダイレクトは自動で追わないか、追うたびに同じ検証をやり直す
- [ ] スキームは `https`（必要なら `http`）に限り、`file:` `gopher:` 等を拒否する
- [ ] 応答サイズとタイムアウトに上限を設ける

## シークレット管理

- [ ] APIキー・DB接続情報・署名鍵等をリポジトリにコミットしない（`.gitignore`で環境変数ファイルを除外する）
- [ ] 開発環境はローカルの環境変数ファイル、本番環境はホスティング先のシークレットストア
      （プラットフォーム提供のSecrets機能等）で管理し、両者を明確に使い分ける
- [ ] クライアントバンドルに含まれる環境変数（フレームワークが公開用と定めるプレフィックスが
      付いたもの等）と、サーバー専用の環境変数を区別し、後者を誤ってクライアントに埋め込まない
- [ ] シークレットが漏洩した場合のローテーション手順（該当キーの無効化・再発行・関連サービスへの
      反映）を事前に決めておく
- [ ] 誤ってGit履歴にシークレットが混入した場合は、単に最新コミットで削除するだけでは
      履歴に残り続けるため、該当シークレット自体を無効化・再発行したうえで、履歴の書き換えを
      検討する

## 依存関係とサプライチェーンの管理

npm パッケージの乗っ取り（正規パッケージに悪意ある版が公開され、インストール時に認証情報を
盗む）は、既知の脆弱性の有無とは関係なく起きる。監査ツールで検出する対策と、取り込む経路を
狭める対策の両方を行う。

**既知の脆弱性を検出する**

- [ ] ロックファイル（`package-lock.json`/`pnpm-lock.yaml`等）をリポジトリにコミットし、
      CI ではロックファイルどおりにだけ入れるコマンド（`npm ci`、`pnpm install --frozen-lockfile` 等）を使う
- [ ] 依存の脆弱性監査（`npm audit --audit-level=high`、`pnpm audit --audit-level high` 等）を
      CI で毎回実行し、High 以上が1件でもあればビルドを失敗させる（「脆弱性ゼロ」の定義の条件1）
- [ ] 監査は公開後も定期実行する（CI の定期ジョブ、Dependabot / Renovate のセキュリティ更新等）
- [ ] サポート期間が終わったランタイム・フレームワーク（Node.js の EOL 版等）を使わない

**取り込む経路を狭める**

- [ ] 公開されたばかりの版をすぐに入れない。パッケージマネージャの待機期間の設定
      （pnpm の `minimumReleaseAge` 等）や、更新ツールの待機設定で数日空ける。乗っ取られた版は
      多くの場合、公開後数日以内に発見・削除される
- [ ] 依存パッケージのインストール時スクリプト（`postinstall` 等）を既定で実行しない
      （npm は `ignore-scripts=true`、pnpm は許可したパッケージだけ実行する設定）。
      ビルドに必要なパッケージだけ個別に許可する
- [ ] 新しい依存を追加するときは、保守状況・ダウンロード数・提供元を確かめ、類似名の
      パッケージ（タイポスクワッティング）でないことを確認する。数行で書ける機能のために
      依存を増やさない
- [ ] 依存の更新は自動化ツールで PR として受け取り、差分と変更履歴を見てから取り込む

**CI/CD を守る**

- [ ] GitHub Actions のサードパーティ製アクションは、タグではなくコミット SHA で固定する
      （`uses: owner/action@<40桁のSHA> # v4.1.0` のように版をコメントで残す）
- [ ] ワークフローの `permissions` は既定で `contents: read` にし、必要なジョブだけ広げる
- [ ] `pull_request_target` で PR 側のコードをチェックアウトして実行しない
      （外部からの PR にシークレットを渡すことになる）
- [ ] 本番デプロイの認証情報は長期の鍵ではなく、OIDC 等の短命な認証を優先する

**ブラウザで読み込む外部スクリプト**

- [ ] CDN から読み込むスクリプト・スタイルには SRI（`integrity` 属性）を付けるか、
      自サイトから配信する
- [ ] 解析タグ等のサードパーティスクリプトは数を絞り、CSP の許可ドメインと一致させる

## ログと監査

**記録すべきイベント**

- ログイン成功・失敗、パスワード変更、権限変更
- 重要なデータの作成・更新・削除（誰が・いつ・何を）
- 認可エラー（権限のない操作の試行）
- 異常なアクセスパターン（短時間の大量リクエスト等）

**ログに書いてはいけないもの**

- [ ] パスワード（平文・ハッシュ問わず）
- [ ] APIキー・トークン・セッションID
- [ ] クレジットカード番号等の決済情報
- [ ] 個人情報の全量（氏名・住所・電話番号等をログに丸ごと出力しない。識別子のみに留める）

## エラー処理（閉じる側に倒す）

**原則: 想定外の状態では「拒否」「中断」の側に倒す。** 認可・署名検証・決済確認などの
判定処理で例外が起きたときに、処理を続行させない。

- [ ] 認可・署名検証・外部の認証基盤への問い合わせが失敗・タイムアウトした場合は、
      リクエストを拒否する（例: 401 / 403 / 503）。「確かめられなかったので通す」にしない
- [ ] 必須の設定値（署名シークレット、許可オリジン等）が未設定・空のときは、起動を失敗させるか
      該当処理を拒否する
- [ ] 利用者に返すエラーは汎用のメッセージと問い合わせ用の ID に留め、スタックトレース・
      SQL・内部パス・ライブラリのバージョンを返さない。詳細はサーバー側のログにだけ残す
- [ ] 複数の書き込みを伴う処理はトランザクションにまとめ、途中で失敗したら全体を戻す
- [ ] 捕まえた例外を握りつぶさない（空の `catch` を置かない）。記録してから適切な応答を返す
- [ ] 未捕捉の例外を最上位で受け止める仕組み（フレームワークのエラーハンドラ等）を置き、
      そこでも詳細を利用者に返さない

## レート制限とabuse対策

| 対象 | 指針 |
|---|---|
| 適用すべきエンドポイント | ログイン、パスワードリセット、会員登録、問い合わせフォーム、検索API等、悪用・ブルートフォースの対象になりやすいエンドポイント |
| 制限の単位 | IPアドレス単位に加え、可能であればアカウント単位でも制限する（IP偽装・分散攻撃への耐性を上げるため） |
| CAPTCHA/ボット対策 | レート制限だけで防ぎきれない自動化されたスパム・ブルートフォースに対する補助的な位置づけとし、正規ユーザーの体験を過度に損なわない範囲で導入を検討する |

## メール送信ドメインの保護

アプリからメール（会員登録の確認、パスワードリセット等）を送る場合、または独自ドメインを
使う場合に適用する（L1必須（独自ドメインを使う場合）／L2必須／L3必須）。

- [ ] 送信に使うドメインに SPF・DKIM・DMARC を設定し、DNS の TXT レコードで確かめる
- [ ] DMARC は `p=none` で観測を始め、レポートで正規の送信元がすべて通ることを確かめてから
      `p=quarantine` / `p=reject` に上げる
- [ ] メールを送らないドメインにも `v=spf1 -all` と `p=reject` の DMARC を設定し、なりすましに
      使われないようにする

## 脆弱性の受付と対応期限

公開後に見つかる脆弱性（自分で見つけたもの、外部から報告されたもの、依存パッケージで新しく
公開されたもの）を、いつまでに直すかを公開前に決める。

- [ ] 報告窓口を用意し、`/.well-known/security.txt`（RFC 9116）に連絡先（`Contact:`）と
      有効期限（`Expires:`）を書く。GitHub で公開するリポジトリでは `SECURITY.md` も置く
- [ ] 重大度ごとの対応期限を決めて設計書に書く。目安（公式の基準ではない）:

| 重大度 | 対応期限の目安 |
|---|---|
| Critical | 24〜72時間以内に修正または緩和策を適用する |
| High | 7日以内 |
| Medium | 30日以内 |
| Low | 次回の定期更新で対応するか、理由を付けて受容する |

- [ ] 受容した指摘は、理由・影響範囲・見直し期限を一覧に残し、期限が来たら見直す
      （「脆弱性ゼロ」の定義の条件2）

## バックアップと復旧

- [ ] DB のバックアップを自動で取得し、保持期間を決めている（L2必須／L3必須）
- [ ] バックアップからの復元手順を一度実際に試している。試していないバックアップは
      復旧できる保証がない（L2推奨／L3必須）
- [ ] バックアップへのアクセス権限は本番 DB と同等以上に絞る

## リリース前セキュリティチェックリスト

各項目の ✅ には根拠（コマンドの出力、ツールの結果、本番の応答等）を付ける。
根拠のない ✅ は ❌ として扱う（「脆弱性ゼロ」の定義の条件3）。

### L1（公開情報のみ）

- [ ] 「脆弱性ゼロ」の定義の3条件を満たしている（依存監査で High 以上0件・未分類の指摘なし・根拠のない ✅ なし）
- [ ] 全ページHTTPS化・HSTS設定済み
- [ ] フォーム入力のサーバー側バリデーション実装済み
- [ ] 依存パッケージの脆弱性監査を CI に組み込み、High 以上で失敗する設定になっている
- [ ] ロックファイルをコミットし、CI はロックファイルどおりにインストールしている
- [ ] セキュリティヘッダ（`Content-Security-Policy`、`Strict-Transport-Security`、
      `X-Content-Type-Options`、`Referrer-Policy`、`frame-ancestors` または `X-Frame-Options`）を
      本番 URL の応答で確かめた。静的サイトで nonce を使えない場合は、hash ベースか
      `script-src 'self'` の CSP にする
- [ ] 本番環境でデバッグ情報・詳細エラーが露出していない
- [ ] シークレットがリポジトリとクライアントのバンドルに含まれていない
- [ ] DB・BaaS を使う場合は、全テーブルで行レベルの制御（RLS / Security Rules）が有効になっている
- [ ] 報告窓口（`security.txt`）と対応期限が決まっている

### L2（個人情報を扱う）

- [ ] L1の全項目を満たしている
- [ ] パスワードはbcrypt/argon2でハッシュ化されている
- [ ] ログイン試行にレート制限がかかっている
- [ ] セッションCookieに`HttpOnly`/`Secure`/適切な`SameSite`が設定されている
- [ ] アクセス制御（認可）が全エンドポイントでサーバー側チェックされ、他人のリソースへの
      アクセスが拒否されることを自動テストで確かめている
- [ ] CORS・ログイン後の戻り先が許可リストで制限されている
- [ ] 認可・署名検証などの判定処理が、失敗時に拒否する側に倒れる
- [ ] ログに機微情報が出力されていないことを確認済み
- [ ] シークレットのローテーション手順が決まっている
- [ ] 送信ドメインに SPF・DKIM・DMARC が設定されている（メールを送る場合）
- [ ] DB のバックアップが自動で取得されている

### L3（決済・認証情報・要配慮個人情報を扱う）

- [ ] L1・L2の全項目を満たしている
- [ ] 決済処理は自前実装せず、外部の決済サービスに委譲している
- [ ] 多要素認証を提供している
- [ ] 機微データが保存時も暗号化されている
- [ ] 監査ログが改ざん困難な形で保存され、一定期間保持されている
- [ ] アクセス権限が業務上必要な最小限に絞られている（最小権限の原則）
- [ ] データ保持期間・削除方針が明文化されている
- [ ] バックアップからの復元を実際に試している
- [ ] セキュリティ専門家または弁護士によるレビューを実施済み、または実施予定である
