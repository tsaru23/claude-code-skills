# アーキテクチャ決定リファレンス

webapp-blueprint スキルの Phase 3（アーキテクチャ決定）で参照する。判断基準を表と決定木の形式でまとめる。

## レンダリング戦略の決定木

4軸: コンテンツの更新頻度／ユーザーごとの出し分けの有無／SEO要件／初期表示速度の要求。

```
ユーザーごとに表示内容が変わるか？
├─ No（全員に同じ内容を表示）
│   └─ コンテンツの更新頻度は？
│       ├─ 低い（ビルド時に確定できる） → SSG
│       ├─ 中程度（数分〜数時間ごとに更新） → ISR
│       └─ 高い（リアルタイムに近い） → SSR、またはストリーミングSSR
└─ Yes（ログイン状態・権限・パーソナライズ等で出し分け）
    └─ SEO要件はあるか？
        ├─ Yes（検索流入が必要なページ）
        │   └─ 初期表示速度の要求は高いか？
        │       ├─ 高い → ストリーミングSSR（重い部分だけ遅延）
        │       └─ 通常 → SSR
        └─ No（ログイン後の管理画面等、検索流入不要）
            └─ CSR（クライアントサイドレンダリング）
```

補足: ページ内で更新頻度の異なる領域が混在する場合（例: 静的な記事本文＋動的なコメント欄）は、ページ全体を1方式に決めず「アイランドアーキテクチャ」で領域ごとに戦略を分ける選択肢がある。

| 戦略 | コンテンツ更新頻度 | ユーザー別出し分け | SEO要件 | 初期表示速度 | 典型ケース |
|---|---|---|---|---|---|
| SSG | 低い | なし | あり | 最速 | LP、ドキュメント、更新頻度の低い記事 |
| ISR | 中程度 | なし | あり | 速い | ブログ、商品一覧など定期更新されるコンテンツ |
| SSR | 高い/都度 | あり | あり | 中程度 | ログイン後もSEOが必要なページ、パーソナライズされた公開ページ |
| ストリーミングSSR | 高い/都度 | あり | あり | 高い要求に対応可 | 一部が重いデータ取得に依存するSSRページ |
| CSR | 任意 | あり | なし | 初期表示は遅いが遷移後は速い | ログイン後の管理画面、ダッシュボード |
| アイランドアーキテクチャ | 混在 | 部分的にあり | あり | 最速（動的部分のみJS） | コンテンツ主体で一部だけインタラクティブなサイト |

## ディレクトリ構成のパターン

### 比較

| 方式 | 概要 | 向いている規模 | 弱点 |
|---|---|---|---|
| レイヤー別（技術種類別） | `components/` `hooks/` `utils/` のように技術的役割で分ける | 小規模、ページ数が少ないプロジェクト | 機能が増えると関連ファイルが散らばり、1機能の全体像を把握しにくくなる |
| 機能別（feature-based） | `features/auth/` `features/billing/` のように業務機能単位で分ける | 中〜大規模、複数機能が並行開発される場合 | 機能間の共通処理の置き場所を別途決める必要がある |
| コロケーション | 関連するファイル（コンポーネント・スタイル・テスト・型）を物理的に隣接配置する | 規模を問わず、feature-based内部の整理方針としても併用可能 | ディレクトリの深さやファイル数が増えるとツリーが見づらくなる場合がある |

feature-baseとコロケーションは排他的ではなく、「機能単位で分割し、各機能内部はコロケーションで整理する」という組み合わせが一般的。

### 規模別の推奨

- **小規模（ページ数が少ない、1〜2人開発）**: レイヤー別で十分。過度な分割は理解コストを増やすだけになりやすい。
- **中規模（複数機能が並行開発される、チーム開発）**: 機能別（feature-based）を基本とし、複数機能から参照される共通処理は `shared/` や `common/` に切り出す。
- **大規模（機能数が多い、チームが複数に分かれる）**: 機能別を徹底し、機能間の依存方向をルール化する（例: 特定の機能から他の機能を直接importしない）。

### ツリー例

**例1: レイヤー別（小規模）**

```

```

## データ取得パターン

| 方式 | 概要 | 向いているケース |
|---|---|---|
| サーバーコンポーネント | サーバー上でデータ取得しHTMLに埋め込んで返す | 初期表示速度とSEOを重視する場合、クライアントに機密性の高いロジックを渡したくない場合 |
| ローダー方式（ルーティング時にサーバーでデータ取得） | ルート遷移時にフレームワークのローダー機構でデータを先読み | ページ単位でデータ要件が明確、遷移時のローディング状態を統一管理したい場合 |
| クライアントフェッチ＋キャッシュ | ブラウザ上でAPIを呼び出しキャッシュライブラリで管理 | ログイン後のインタラクティブな画面、ユーザー操作に応じて頻繁に再取得する場合 |

判断の目安: 初回表示に必要なデータはサーバー側（サーバーコンポーネント/ローダー）で取得し、ユーザー操作後の再取得や頻繁な更新が必要な部分はクライアントフェッチ＋キャッシュに任せる、という組み合わせが一般的。

**N+1の回避**: 一覧表示で関連データを個別に取得すると件数分のリクエストが発生する。関連データはJOINやバッチ取得（DataLoaderパターンなど）でまとめて取得し、ループ内で1件ずつ取得する実装を避ける。

**楽観的更新をどこまでやるか**: 楽観的更新（サーバーの応答を待たずにUIを先に更新する）は、失敗時のロールバック処理が必要になり実装コストが上がる。以下を目安に適用範囲を決める。

- 失敗頻度が低く、失敗時の影響が軽微な操作（いいね、既読など） → 楽観的更新が有効
- 失敗時に金銭・データ整合性への影響が大きい操作（決済、削除の確定など） → サーバー応答を待ってから反映する

## 認証・認可のパターン

### セッションCookie方式 vs トークン(JWT)方式

| 観点 | セッションCookie方式 | トークン(JWT)方式 |
|---|---|---|
| 保存場所 | サーバー側にセッション情報、クライアントはCookieのIDのみ保持 | クライアント側にトークン本体を保持（Cookieまたはストレージ） |
| 失効のさせやすさ | サーバー側でセッションを削除すれば即座に失効可能 | 有効期限が来るまで失効させにくい（失効リストの管理が別途必要） |
| XSS耐性 | HttpOnly Cookieを使えばJavaScriptから読み取れず耐性が高い | ストレージに保存すると XSS で窃取されるリスクがある。Cookie保存なら同等の耐性を確保できる |
| CSRF耐性 | Cookie自動送信のためCSRF対策（トークン検証等）が別途必要 | 手動でヘッダーに付与する実装ならCSRFの影響を受けにくい |
| スケール特性 | サーバー側にセッションストアが必要（複数台構成では共有ストアが必要） | サーバー側に状態を持たないため水平スケールしやすい |

判断の目安: 単一のWebアプリで即時失効（強制ログアウト等）が重要ならセッションCookie方式、複数サービス間でのAPI認証やモバイルアプリとの共有が必要ならトークン方式が扱いやすい。どちらもCookie保存時はHttpOnly・Secure・SameSite属性を適切に設定する。

### 認可判定はどの層で行うか

| 層 | 役割 | 向いている判定内容 |
|---|---|---|
| ミドルウェア | リクエストの入口で一括判定 | 未ログインの遮断、ロールによるルート単位の大まかな制御 |
| ルート/ページ | ページ単位の判定 | そのページ固有の権限（特定ロールのみ表示可能なページ等） |
| データ層 | データ取得・更新のクエリ自体に条件を組み込む | レコード単位の所有者チェック、行レベルのアクセス制御 |

**原則: 認可判定をクライアント側だけで行わない。** クライアント側での表示/非表示の出し分けはUX上の配慮に過ぎず、実際のアクセス制御はサーバー側（ミドルウェア／ルート／データ層のいずれか、または組み合わせ）で必ず行う。クライアント側の判定のみに依存すると、APIを直接叩かれた場合に制御が効かない。

## API設計

| 方式 | 選択基準 |
|---|---|
| REST | クライアントが複数種類（Web/モバイル/外部パートナー）存在し、汎用的でキャッシュしやすいAPIが必要な場合。HTTPの意味論（メソッド・ステータスコード）に沿った設計が可能 |
| RPC（tRPC等） | フロントエンドとバックエンドを同一言語・同一リポジトリで開発し、型を共有して開発速度を優先したい場合。外部公開APIには不向き |
| GraphQL | クライアントごとに必要なフィールドが大きく異なる、画面の要求に応じて柔軟に取得項目を変えたい場合。学習コストとサーバー側の実装コストは相対的に高い |
| Server Actions（フレームワーク組み込みのサーバー処理呼び出し） | フォーム送信やミューテーションが中心で、独立したAPI層を設ける必要がない単一アプリ構成の場合 |

判断の目安: 外部公開や複数クライアント対応が前提ならREST、フロントエンドとバックエンドが一体開発でクライアントが単一ならRPCまたはServer Actions、クライアントごとの取得要件の差が大きいならGraphQLを検討する。

### バージョニングの例

パスにバージョンを含める方式が分かりやすい。

```
/api/v1/users
/api/v2/users
```

破壊的変更を含む場合は新しいバージョンを追加し、旧バージョンは廃止予告期間を設けてから撤去する。

### エラーレスポンスの統一形式の例

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります。",
    "details": [
      { "field": "email", "message": "メールアドレスの形式が正しくありません。" }
    ]
  }
}
```

`code` は機械判定用の一意な識別子、`message` は人間向けの説明、`details` はフィールド単位の補足情報という3要素を基本形にすると、クライアント側のエラーハンドリングを統一しやすい。

## 状態の置き場所

| 分類 | 内容の例 | 適切な置き場所 |
|---|---|---|
| サーバー状態 | DBに保存されたデータ、APIから取得する情報 | サーバーコンポーネント／ローダー／クライアントフェッチ用キャッシュライブラリ |
| URL状態 | ページ番号、フィルタ条件、選択中のタブ、検索キーワード | クエリパラメータ／パスパラメータ |
| クライアント状態 | モーダルの開閉、UIのテーマ切り替え、ドラッグ中の一時状態 | コンポーネントローカルのstate、必要な場合のみ軽量な状態管理ライブラリ |
| フォーム状態 | 入力中の値、バリデーションエラー、送信中フラグ | フォーム専用のライブラリ、またはコンポーネントローカルのstate |

判断の目安: 「ページをリロードしても復元したい状態」はURL状態、「サーバーの最新値を反映すべき状態」はサーバー状態として扱う。両者に当てはまらない一時的なUI操作のみをクライアント状態に置く。

## 環境分離と設定管理

- **環境変数の命名規約**: プレフィックスで用途を区別する（例: `NEXT_PUBLIC_` のようにクライアント公開用を明示するプレフィックスを持つフレームワークではそれに従う）。環境（開発/ステージング/本番）ごとに値を切り替え、環境名自体は変数名に含めず値側で管理する。
- **クライアント公開変数とサーバー専用変数の分離**: クライアントバンドルに含まれてよい値（公開APIのエンドポイントURL等）と、サーバーでしか使わない値（DB接続文字列、APIシークレット等）を明確に分離する。フレームワークが提供する公開変数の命名規則に従い、サーバー専用の値に誤って公開用プレフィックスを付けない。
- **シークレットをリポジトリに置かない**: `.env` ファイル等はバージョン管理から除外し、シークレット管理サービスや環境ごとの設定画面から注入する。誤ってコミットされた場合は値のローテーション（再発行）まで行う。

## デプロイ構成

- **3面構成**: プレビュー環境（プルリクエストごとに自動生成される一時環境）／ステージング（本番相当のデータ・構成で最終確認を行う環境）／本番。個人開発など体制が小さい場合はプレビュー環境と本番の2面から始め、必要になった段階でステージングを追加する。
- **マイグレーションの適用タイミング**: アプリケーションのデプロイより前にマイグレーションを適用し、新旧バージョンのアプリケーションが同じスキーマに対して動作できる状態を保つ。破壊的なスキーマ変更（列の削除等）は、まず新しい列を追加してアプリケーション側を移行し、参照がなくなったことを確認してから旧列を削除する、という段階的な手順を踏む。
- **ロールバック戦略**: アプリケーションのロールバックは直前のデプロイに戻すだけで済む構成を保つ。データベースのマイグレーションは基本的に前方互換（ロールバック後の旧バージョンでも動作する）を意識して設計し、ロールバックのたびにスキーマを戻す運用は避ける。

## 段階的に複雑さを足す指針

| 最初から入れるもの | 必要になってから入れるもの |
|---|---|
| 基本的なエラーハンドリングとログ出力 | 分散トレーシング、APM（アプリケーションパフォーマンス監視） |
| 環境変数によるシークレット分離 | シークレット管理専用サービスの導入 |
| 単一のデータストア | キャッシュ層（Redis相当のKVストア等） |
| シンプルなCI（テスト＋デプロイ） | 複雑なリリースパイプライン（カナリアリリース、段階的ロールアウト） |
| モノリシックな1つのアプリケーション/APIサーバー | マイクロサービスへの分割 |
| 手動または簡易なバックアップ | 詳細なDR（災害復旧）計画、マルチリージョン構成 |
| 基本的な認証・認可 | SSO、多要素認証、詳細な監査ログ |

判断の目安: 「今のトラフィック・チーム規模で本当に必要か」を基準に導入時期を決める。将来の成長を見越した先回りの複雑化は、実際にボトルネックが顕在化してから対応する方針の方が、多くの場合総コストを抑えられる。
