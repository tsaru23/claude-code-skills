# 品質基準（パフォーマンス・アクセシビリティ・SEO・テスト）

Webアプリケーションの設計書に品質基準を転記するための参照資料である。散文の解説より
チェック可能な項目表を主体とする。数値目標のうち公式に定義されているものは断定し、
それ以外は「目安」であることを明示する。

## パフォーマンス予算

### Core Web Vitals

Googleが定義する公式の閾値は次のとおりである（この3指標のしきい値は公式仕様）。

| 指標 | 内容 | Good（良好） | Needs Improvement | Poor |
|---|---|---|---|---|
| LCP（Largest Contentful Paint） | 最大コンテンツの描画完了までの時間 | 2.5秒以下 | 2.5〜4.0秒 | 4.0秒超 |
| INP（Interaction to Next Paint） | ユーザー操作への応答性 | 200ミリ秒以下 | 200〜500ミリ秒 | 500ミリ秒超 |
| CLS（Cumulative Layout Shift） | 累積レイアウトシフト量 | 0.1以下 | 0.1〜0.25 | 0.25超 |

サイト種別ごとの現実的な閾値（以下は目安であり公式値ではない。プロジェクトの実測値に
応じて調整する）:

| サイト種別 | LCP目安 | INP目安 | CLS目安 | 補足 |
|---|---|---|---|---|
| LP・コーポレートサイト | 2.5秒以下を目指す | 200ミリ秒以下を目指す | 0.1以下を目指す | Core Web VitalsのGood基準をそのまま適用しやすい |
| 通常のWebアプリ（ログイン後の画面等） | 2.5〜3.5秒程度を許容範囲とする | 200ミリ秒以下を目指す | 0.1以下を目指す | 初回ロードよりインタラクション応答性を優先する |
| 3D体験型・リッチメディア | 4秒程度まで許容し、代わりにローディング表現でユーザーの体感を補う | 200〜300ミリ秒程度を許容 | 0.1以下を目指す（3D領域自体のシフトは対象外にできる） | Core Web Vitals準拠が難しい場合は理由を設計書に明記し、代替のUX配慮（プログレス表示等）を併記する |

### バンドルサイズ・アセット予算

以下は一般的な目安であり、プロジェクトの性質に応じて調整する。

| 項目 | 目安 |
|---|---|
| JavaScript初回ロード（gzip圧縮後） | 数百KB以内を目安にする。ページ種別ごとに予算を分けてもよい |
| 画像（1枚あたり） | 表示サイズに対して過大な解像度で配信しない。次世代フォーマットで圧縮する |
| Webフォント（合計） | 使用するウェイト・文字セットを絞り、サブセット化する |

### 測定方法とCIで落とす基準

- 測定方法: Lighthouse等のラボ計測に加え、実ユーザー計測（RUM: Real User Monitoring）で
  実際の利用環境での分布を把握する。ラボ計測と実ユーザー計測は乖離しうるため両方を見る。
- CIでの品質ゲート運用の目安:
  - [ ] PRごとにLighthouse等の自動計測を実行する
  - [ ] スコアやCore Web Vitalsが定めた閾値を下回った場合にビルドを失敗させるか、
        レビュー必須の警告を出す
  - [ ] 閾値は初期リリース時点の実測値を基準にし、劣化（リグレッション）を検知する運用にする
        （厳しすぎる絶対値をいきなり課さない）

パフォーマンス予算設定のイメージ（Lighthouse CI相当の予算定義の擬似形式）:

```json
{
  "path": "/*",
  "resourceSizes": [
    { "resourceType": "script", "budget": 300 },
    { "resourceType": "image", "budget": 500 },
    { "resourceType": "font", "budget": 150 }
  ],
  "timings": [
    { "metric": "largest-contentful-paint", "budget": 2500 },
    { "metric": "cumulative-layout-shift", "budget": 0.1 }
  ]
}
```

数値（`budget`の単位はKB・ミリ秒）はプロジェクトごとの実測値に基づいて調整する目安であり、
上記はあくまで設定形式のイメージである。

## 画像・フォント・アセット最適化

- [ ] 画像は次世代フォーマット（WebP、AVIF等）を優先し、非対応環境向けのフォールバックを用意する
- [ ] レスポンシブ画像（`srcset`/`sizes`、または相当の仕組み）で画面サイズに応じた解像度を配信する
- [ ] 画面外の画像は遅延読み込み（`loading="lazy"`）にする
- [ ] 最初に表示される主要画像（LCP対象）には`fetchpriority="high"`等で優先度を明示し、
      遅延読み込みの対象から外す
- [ ] Webフォントはサブセット化し、使用しない文字・ウェイトを含めない
- [ ] フォント読み込み中の表示制御に`font-display: swap`等を指定し、テキスト非表示時間を減らす
- [ ] 画像・広告枠・埋め込みコンテンツには事前に`width`/`height`（またはaspect-ratio）を指定し、
      読み込み完了時のレイアウトシフトを防ぐ

## アクセシビリティ

WCAG 2.2のAAレベルを基準とする。

| チェック項目 | 内容 | 自動/手動 |
|---|---|---|
| キーボード操作 | すべての操作可能要素にマウスなしで到達・操作できる | 手動確認が必要 |
| フォーカス可視 | フォーカスが当たっている要素が視覚的に判別できる（アウトライン除去のみで代替なしは不可） | 自動チェックで一部拾える |
| コントラスト比 | 通常テキストで4.5:1以上、大きいテキストで3:1以上を確保する | 自動チェックで拾える |
| 代替テキスト | 画像に意味のある`alt`を付与する。装飾目的の画像は空`alt`にする | 自動チェックで欠落は拾えるが、内容の適切さは手動確認が必要 |
| 見出し階層 | `h1`〜`h6`を論理的な階層で使用し、スタイル目的で飛ばさない | 自動チェックで拾える |
| フォームのラベルとエラー通知 | 入力欄にラベルを関連付け、エラーはテキストで明示し色だけに依存しない | 自動チェックでラベル欠落は拾えるが、エラー通知の分かりやすさは手動確認が必要 |
| ランドマーク | `header`/`nav`/`main`/`footer`等のランドマークで構造を示す | 自動チェックで拾える |
| `prefers-reduced-motion`の尊重 | アニメーション・自動再生を減らす設定を尊重する実装にする | 手動確認が必要 |
| 動的更新の通知 | 非同期で更新される領域（通知、バリデーション結果等）をスクリーンリーダーに伝える（`aria-live`等） | 手動確認が必要 |

- [ ] 自動チェックツール（axe等相当のもの）をCIまたは開発フローに組み込む
- [ ] 自動チェックでは拾えない項目（実際のキーボード操作、スクリーンリーダーでの読み上げ、
      エラー通知の分かりやすさ）は、リリース前に手動で確認する

## SEO

- [ ] 各ページに固有の`title`・`meta description`を設定する
- [ ] 正規URL（`canonical`）を設定し、重複コンテンツの評価分散を防ぐ
- [ ] 該当するコンテンツ種別に構造化データ（JSON-LD等）を付与する
- [ ] `sitemap.xml`を生成し、`robots.txt`から参照するか送信する
- [ ] `robots.txt`でクロール対象外のパス（管理画面等）を除外する
- [ ] 多言語展開する場合は`hreflang`で言語・地域ごとのページを関連付ける
- [ ] SPA（クライアントサイドレンダリング主体）の場合、検索エンジンのインデックス対象ページは
      SSR/SSG/プリレンダリングのいずれかで初期HTMLに主要コンテンツを含める
- [ ] OGP（`og:title`/`og:image`等）を設定し、SNSでの共有時の表示を確認する

構造化データの種類はコンテンツに応じて選ぶ。代表的な対応関係は次のとおりである。

| コンテンツの種類 | 構造化データの例 |
|---|---|
| 記事・ブログ | Article / BlogPosting |
| 商品ページ | Product |
| よくある質問 | FAQPage |
| パンくずリスト | BreadcrumbList |
| 組織情報 | Organization |
| イベント | Event |

いずれの場合も、実際にページに表示されている内容と構造化データの内容を一致させる
（表示されていない情報を構造化データにのみ含めない）。

## エラーハンドリングと可観測性

**エラーバウンダリの配置**

- [ ] ページ単位・主要な機能単位でエラーバウンダリを設置し、1箇所のエラーで画面全体が
      白画面にならないようにする
- [ ] エラーバウンダリ配下ではユーザーに再試行手段（再読み込み導線等）を提示する

**ユーザーに見せるエラーと内部ログの分離**

- [ ] ユーザー向けエラーメッセージにはスタックトレース・内部実装・SQL文等を含めない
- [ ] 内部ログには原因究明に必要な詳細情報を記録し、両者を明確に分離する

**エラートラッキングの導入基準**

- L1: 導入は任意。最低限、サーバーログでエラーを追える状態にする
- L2以上: エラートラッキングサービス等でエラーを収集し、発生頻度・影響範囲を可視化することを推奨する

**構造化ログ**

- [ ] ログは機械可読な構造化形式（JSON等）で出力し、検索・集計しやすくする
- [ ] リクエスト単位で追跡できる識別子（トレースID等）を付与する

**監視すべき指標**

| カテゴリ | 指標例 |
|---|---|
| 可用性 | アップタイム、ヘルスチェックの成否 |
| レイテンシ | レスポンスタイムの中央値・p95/p99 |
| エラー率 | HTTP 5xx率、アプリケーションエラー発生率 |

**アラートを鳴らす閾値の考え方**

- 絶対値をいきなり厳しく設定せず、まず指標を可視化してから、平常時のばらつきを踏まえて
  閾値を決める。
- 一時的なスパイクで頻繁に誤報が鳴る閾値は運用が形骸化するため、継続時間（例: 一定時間
  継続して悪化した場合のみ通知）を組み合わせる。

**可観測性のツールカテゴリ**（特定製品ではなく機能カテゴリとして整理する）

| カテゴリ | 役割 |
|---|---|
| エラートラッキング | フロントエンド・バックエンドの例外を収集し、発生箇所・頻度・影響ユーザー数を可視化する |
| APM（アプリケーション性能監視） | レイテンシ・スループット・依存サービス呼び出しのボトルネックを可視化する |
| ログ集約 | 分散した各サービスのログを一元的に検索・集計できるようにする |
| アップタイム監視 | 外形監視により、ユーザー視点でのサービス到達可能性を継続的に確認する |

0→1フェーズではエラートラッキングとアップタイム監視を最優先で導入し、APM・ログ集約は
規模が拡大してから追加する、という優先順位で判断してよい。

## テスト戦略

**テストピラミッド**

```
        ▲
       /E2E\        少数。主要なユーザーフローのみ
      /------\
     /統合テスト\    中程度。API・DB連携など複数コンポーネントの結合
    /----------\
   / 単体テスト  \   多数。関数・コンポーネント単位の振る舞い
  /--------------\
```

- [ ] 単体テストを最も厚く書き、統合テスト・E2Eは対象を絞る（上位層ほど実行コスト・
      メンテナンスコストが高いため）

**0→1フェーズで最低限書くべきテスト（全部書こうとしない指針）**

- [ ] 認証・決済・データ整合性に関わるコアロジックの単体テスト
- [ ] 主要なユーザーフロー（会員登録、ログイン、主要機能の完了までの一連の操作）のE2Eを
      1〜数本
- [ ] 複雑な条件分岐を持つビジネスロジックの単体テスト
- 上記以外（単純なUI表示のみのコンポーネント等）は0→1フェーズでは網羅を狙わず、
  機能が安定してから追加していく方針でよい

**E2Eをどこに絞るか**

- 売上・登録・主要機能の完了に直結するクリティカルパスに限定する。
- 画面のバリエーションをすべてE2Eで検証しようとすると実行時間・メンテナンスコストが
  急増するため、バリエーションの検証は単体・統合テストに任せる。

**視覚回帰テストの費用対効果**

- デザインシステムの一貫性が重要なプロダクト、またはUIコンポーネントライブラリを持つ
  プロダクトでは導入効果が高い。
- 0→1フェーズでUIが頻繁に変わる間は、差分確認の運用コストがメリットを上回りやすいため、
  UIがある程度安定してからの導入を検討する。

## CI/CDの品質ゲート

**PRで必ず走らせるもの**

- [ ] 型チェック
- [ ] Lint
- [ ] 単体テスト・統合テスト
- [ ] ビルド（本番相当の設定でビルドが通ることの確認）

**任意にできるもの（プロジェクトの規模・体制に応じて判断）**

- E2Eテストの全量実行（PRごとではなく、マージ前後や定期実行に留める選択肢もある）
- 視覚回帰テスト
- パフォーマンス計測の自動実行

**プレビューデプロイの活用**

- [ ] PRごとに独立したプレビュー環境を自動生成し、実際の動作確認をレビュー前に行えるようにする
- [ ] プレビュー環境のURLをPR上で確認できるようにし、レビュアーがコードを読むだけでなく
      実際に触って確認できるようにする

## リリース判定の基準表

「これを満たさないとリリースしない」項目の一覧。プロジェクトごとに過不足を調整するが、
削除する場合は理由を設計書に明記する。

- [ ] `references/security-baseline.md`のリリース前セキュリティチェックリスト（該当レベル分）を満たしている
- [ ] PRの品質ゲート（型チェック・Lint・テスト・ビルド）がすべて通過している
- [ ] Core Web Vitalsが目標範囲内、または乖離の理由と対応方針が設計書に明記されている
- [ ] アクセシビリティの自動チェックが通過し、手動確認項目（キーボード操作・スクリーン
      リーダー等）を実施済みである
- [ ] 主要なユーザーフローのE2Eが通過している
- [ ] エラートラッキング・監視の仕組みが稼働しており、アラートの通知先が設定されている
- [ ] SEOの必須項目（`title`/`meta description`/`sitemap.xml`/`robots.txt`）が設定されている
- [ ] ロールバック手順（デプロイ失敗時に前バージョンへ戻す方法）が確認済みである
