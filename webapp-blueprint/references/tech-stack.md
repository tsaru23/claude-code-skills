# 技術スタック選定リファレンス

webapp-blueprint スキルの Phase 2（技術スタック選定）で参照する。判断基準を表と決定木の形式でまとめる。散文での説明は最小限にとどめる。

## 選定の原則

1. **運用人数に対して過剰な構成を選ばない。** 1〜2人で保守するプロダクトにマイクロサービス構成や自前Kubernetesクラスタは不要。運用者の人数・スキルセットに見合う複雑さに抑える。
2. **枯れた技術を優先する。** リリース直後のメジャーバージョンやRC版は、情報量が少なく破壊的変更のリスクも高い。安定運用が目的なら実績のあるバージョンを選ぶ。
3. **ロックインの度合いを意識する。** 特定ベンダーの独自APIに強く依存する構成は、移行コストとセットで評価する。ロックイン自体が悪いわけではなく、「気づかずに深くロックインする」ことが問題。
4. **「使ったことがある」は正当な選定理由である。** 理論上の最適解より、チームが習熟している技術の方が総コストで勝ることが多い。新技術の採用は学習コストを明示的に見積もった上で判断する。
5. **要件から逆算する。** トラフィック規模、更新頻度、チームの体制、予算上限を先に確定させてから技術を選ぶ。技術先行で要件を後付けしない。

## プロダクト種別 × 推奨スタック対応表

各セルは「軽量案 / 標準案 / スケール案」の3段階。軽量案は個人開発・小規模、標準案は小〜中規模チームでの本番運用、スケール案は高トラフィックや大規模組織を想定。

### LP・コーポレートサイト

| レイヤー | 軽量案 | 標準案 | スケール案 |
|---|---|---|---|
| フロントエンド | 素のHTML+バンドラなし、Astro | Astro、Next.js(SSG) | Next.js(SSG/ISR) |
| バックエンド | 不要 | 不要（フォームはSaaS連携） | 軽量API（問い合わせ・フォーム処理のみ） |
| データストア | 不要 | 不要 | ヘッドレスCMS |
| ホスティング | 静的ホスティング | 静的ホスティング/エッジPaaS | エッジPaaS+CDN |

### Webアプリ（認証あり）

| レイヤー | 軽量案 | 標準案 | スケール案 |
|---|---|---|---|
| フロントエンド | Next.js、SvelteKit | Next.js、Remix | Next.js、Nuxt |
| バックエンド | BaaS（Supabase/Firebase） | フレームワーク組み込み+BaaS | 独立APIサーバー（Hono/NestJS等） |
| データストア | BaaS内蔵DB（PostgreSQL系） | PostgreSQL（マネージド） | PostgreSQL+キャッシュ層(KV/Redis相当) |
| ホスティング | エッジ系PaaS | エッジ系PaaS/コンテナ系PaaS | コンテナ系PaaS/IaaS |

### EC（オンラインショップ）

| レイヤー | 軽量案 | 標準案 | スケール案 |
|---|---|---|---|
| フロントエンド | ECプラットフォームのテーマ機能 | Next.js+ヘッドレスコマース | Next.js+ヘッドレスコマース |
| バックエンド | ECプラットフォーム（Shopify等）に一任 | ヘッドレスコマースAPI連携 | 独立APIサーバー+決済/在庫の外部連携 |
| データストア | プラットフォーム側に一任 | プラットフォーム側+補助DB | PostgreSQL+キャッシュ層 |
| ホスティング | プラットフォーム側に一任 | エッジ系PaaS | コンテナ系PaaS |

決済・在庫・注文管理を自前実装するかどうかは、この対応表とは別に「決済代行/コマースSaaSの機能で要件を満たせるか」を最初に確認する。満たせるなら自前実装は避ける。

### メディア・CMS

| レイヤー | 軽量案 | 標準案 | スケール案 |
|---|---|---|---|
| フロントエンド | Astro | Astro、Next.js(SSG/ISR) | Next.js(ISR) |
| バックエンド | ヘッドレスCMSに一任 | ヘッドレスCMSに一任 | ヘッドレスCMS+配信最適化API |
| データストア | ヘッドレスCMS内蔵 | ヘッドレスCMS内蔵 | ヘッドレスCMS+CDNキャッシュ |
| ホスティング | 静的ホスティング | エッジ系PaaS | エッジ系PaaS+CDN |

### ダッシュボード・管理画面

| レイヤー | 軽量案 | 標準案 | スケール案 |
|---|---|---|---|
| フロントエンド | Vite+SPA | Next.js、Remix | Next.js |
| バックエンド | BaaS | フレームワーク組み込み/独立API | 独立APIサーバー |
| データストア | BaaS内蔵DB、SQLite | PostgreSQL | PostgreSQL+分析用途の別系統（DWH等） |
| ホスティング | エッジ系PaaS | エッジ系PaaS/コンテナ系PaaS | コンテナ系PaaS/IaaS |

### 体験型サイト（3D/インタラクティブ）

| レイヤー | 軽量案 | 標準案 | スケール案 |
|---|---|---|---|
| フロントエンド | Vite+SPA（Three.js等を直接利用） | Next.js+WebGLライブラリ | Next.js+WebGLライブラリ+アセット配信最適化 |
| バックエンド | 不要 | 軽量API（スコア保存等が必要な場合のみ） | 独立APIサーバー |
| データストア | 不要 | KV、SQLite | PostgreSQL、KV |
| ホスティング | 静的ホスティング | エッジ系PaaS | エッジ系PaaS+専用CDN（大容量アセット） |

3D/インタラクティブ系はアセット（モデル・テクスチャ・動画）の配信コストが支配的になりやすい。フレームワーク選定より先に、アセット配信経路（CDN、圧縮、遅延読み込み）を検討する。

## レイヤー別の選択肢比較

### フレームワーク

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| Next.js | 認証あり・SEO要件ありのWebアプリ、幅広いエコシステムが欲しい場合 | シンプルな静的サイトのみで機能過剰になる場合 |
| Remix (React Router v7) | フォーム主体でサーバー連携が多いアプリ、Web標準に近い書き方を好む場合 | 静的サイト中心の要件 |
| Astro | コンテンツ主体でインタラクティブ性が低いサイト（LP、メディア） | 認証や複雑な状態管理を伴うアプリ |
| SvelteKit | バンドルサイズを抑えたい、Svelteの記法を好むチーム | Reactエコシステムの資産を流用したい場合 |
| Nuxt | Vueで統一されたチーム、Vueエコシステムを活用したい場合 | チームにVue経験者がいない場合 |
| Vite+SPA | 管理画面やツール系で認証後の画面のみ、SEO不要 | SEOが必要、初期表示速度が重要な公開サイト |
| 素のHTML+バンドラなし | 数ページ以下の極小サイト、更新頻度が極めて低い | 少しでも動的な要素・状態管理が必要になる見込みがある |

### スタイリング

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| Tailwind CSS | 迅速なプロトタイピング、デザインシステムの一貫性を保ちたい場合 | クラス名の可読性を重視するチーム文化 |
| CSS Modules | コンポーネント単位でスコープを閉じたい、既存CSS資産の移行 | ユーティリティファーストで素早く書きたい場合 |
| vanilla-extract | 型安全なスタイルとゼロランタイムを両立したい場合 | 学習コストをかけたくない小規模プロジェクト |
| CSS-in-JS（ランタイム型） | 動的なテーマ切り替えが多く、実行時スタイル生成が必要な場合 | パフォーマンスを最優先する大規模アプリ（ランタイムコストに注意） |

### UIコンポーネント

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| shadcn/ui（コピー＆ペースト方式） | デザインの細部までカスタマイズしたい、依存パッケージを増やしたくない場合 | コンポーネント数が多くメンテナンス工数を割けない場合 |
| MUI等のフル装備ライブラリ | 管理画面など短期間で機能を揃えたい、デザインの独自性を求めない場合 | ブランド独自のデザインを強く出したいプロダクト |
| 自作 | 極めて特殊なUI要件、コンポーネント数が少ない場合 | 一般的なUIパターンが多く、車輪の再発明になる場合 |

コピー＆ペースト方式（shadcn/ui等）の利点は、コンポーネントのソースコードが手元にあるため自由に改変でき、パッケージのメジャーアップデートに振り回されないこと。欠点は、アップストリームの修正やアクセシビリティ改善を自動で受け取れず、自分のコードベースに複製されたコンポーネントを自分で保守する責任が発生すること。

### 状態管理

**原則: まず状態管理ライブラリを入れないで済まないか疑う。** サーバーから取得したデータはサーバー状態、URLで表現できるものはURL状態として扱えば、クライアント側の状態管理ライブラリなしで成立するケースは多い。

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| URL/サーバー状態のみ（ライブラリなし） | フィルタ条件・ページネーション・選択中タブなどURLで表現可能な状態が中心 | クライアントだけで完結する複雑なUI状態が多い場合 |
| TanStack Query | サーバーデータの取得・キャッシュ・再検証が中心の要件 | サーバーとやり取りしないクライアント専用の状態 |
| Zustand | グローバルなクライアント状態が少数あり、軽量に済ませたい場合 | 状態遷移が複雑でミドルウェアや厳密な構造が必要な場合 |
| Redux Toolkit | 状態遷移が複雑、DevToolsでの時系列デバッグが重要、大規模チームで規約を統一したい場合 | 小規模アプリでボイラープレートが見合わないケース |

### バックエンド

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| BaaS（Supabase/Firebase等） | 認証・DB・ストレージを短期間で揃えたい、小〜中規模 | 複雑なビジネスロジックが多く、ベンダー固有の制約が障害になる場合 |
| フレームワーク組み込みのサーバー機能 | フロントエンドと同一リポジトリで完結させたい、API単体で公開する必要がない | モバイルアプリ等、複数クライアントに同一APIを提供する必要がある場合 |
| 独立したAPIサーバー（Hono/Fastify/NestJS等） | 複数クライアント（Web/モバイル/外部連携）が同じAPIを使う、チームでフロントとバックを分業する場合 | 単一のWebフロントエンドのみで完結し、分離のメリットが薄い小規模構成 |

### データベース

決定木:

```
更新頻度・同時書き込みは多いか？
├─ Yes（複数ユーザーが同時に書き込む一般的なWebアプリ）
│   └─ リレーショナルな整合性が必要か？
│       ├─ Yes → PostgreSQL（第一候補）／MySQL（既存資産や運用経験がある場合）
│       └─ No（スキーマが流動的、ネスト構造が中心）→ ドキュメントDB
├─ No（読み取り中心、単一ライターで足りる、個人開発・小規模）
│   └─ SQLite（+ 複数拠点からの読み取りが必要ならリモートSQLite）
└─ 用途がキャッシュ・セッション・レート制限など一時的な値の保持のみ
    └─ KV（Key-Value）
```

補足: PostgreSQLは拡張機能（全文検索、地理情報等）が豊富で、迷ったときの既定の選択肢になりやすい。SQLiteはファイル1つで完結する手軽さが利点だが、書き込みの同時実行性に制約があるため、同時書き込みが多い一般的なWebアプリには不向き。

### ORM/クエリ

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| Prisma | スキーマ定義から型を生成し開発速度を優先したい場合 | 複雑なクエリを細かく制御したい、マイグレーションの挙動を完全に把握したい場合 |
| Drizzle | SQLに近い書き味を保ちつつ型安全性も欲しい場合 | チームがSQLに不慣れでスキーマ定義言語の抽象度を優先したい場合 |
| 素のSQL | クエリの挙動を完全に制御したい、パフォーマンスチューニングが重要な箇所 | 開発速度を優先したい、チーム全体がSQLに習熟していない場合 |

### 認証

**原則: 自前実装は避ける。** パスワードハッシュ化、セッション管理、トークン失効、各種攻撃への対策を独自実装すると、セキュリティ上の欠陥を生みやすい。既存のライブラリ・サービスに任せられる部分は任せる。

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| 認証ライブラリ（Auth.js等） | フレームワークに統合された形で認証を実装したい、外部サービスへの依存を減らしたい場合 | エンタープライズ向けのSSO・多要素認証・監査ログを標準機能として求められる場合 |
| IDaaS（Auth0, Clerk, Amazon Cognito等） | SSO、多要素認証、ユーザー管理画面などを既製品で揃えたい場合 | 小規模プロジェクトでコストや外部依存を最小化したい場合 |
| BaaS内蔵認証 | すでにBaaSを採用しており、DBと認証を一体で管理したい場合 | 認証機能だけを他のバックエンド構成から独立させたい場合 |

### ホスティング

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| エッジ系PaaS | グローバルな低レイテンシが欲しい、運用の手間を最小化したい場合 | 長時間実行のバッチ処理やエッジの実行時間制約に収まらない処理が必要な場合 |
| コンテナ系PaaS | 既存のDockerイメージを流用したい、長時間実行のプロセスが必要な場合 | インフラの完全な制御や独自のネットワーク構成が必要な場合 |
| IaaS | インフラ構成を細部まで制御したい、既存のオンプレ資産と連携する場合 | 運用に割ける人員が少なく、インフラ管理の負担を避けたい場合 |
| 静的ホスティング | 動的なサーバー処理が不要なサイト | 認証・DBアクセス等のサーバーサイド処理が必要な場合 |

## コスト構造の目安

金額は変動するため、「何が課金トリガーになるか」という構造で把握する。

| レイヤー | 無料枠で始められるか | 最初に課金対象になりやすい要素 |
|---|---|---|
| ホスティング（エッジ/静的） | 個人開発・小規模なら多くのサービスで可能 | リクエスト数、帯域幅（大容量アセット配信時に顕在化） |
| ホスティング（コンテナ/IaaS） | 最小構成なら無料枠がある場合も | 常時稼働時間、CPU/メモリの割当量 |
| データベース（マネージド） | 小容量・低接続数なら可能なことが多い | ストレージ容量、同時接続数、バックアップ保持期間 |
| BaaS（認証・DB・ストレージ一体型） | MAU（月間アクティブユーザー）や容量の枠内なら可能 | MAU超過、ストレージ容量、API呼び出し数 |
| IDaaS | 少人数のユーザーなら可能なことが多い | MAU、追加の認証方式（SSO、MFA）の有効化 |
| CDN/アセット配信 | 小規模なら可能 | 転送量（帯域幅）、リクエスト数 |
| 外部API連携（決済、メール送信等） | 少量なら可能 | 送信数・処理件数、トランザクション数 |

判断の指針: 個人開発フェーズでは無料枠内に収まる構成を優先し、想定トラフィックが無料枠の上限に近づく段階で、どのレイヤーが最初に課金対象になるかを見積もった上でスケール案へ移行する。

## 選定してはいけないパターン

1. **要件を確認せずに毎回同じ構成を提案する。** 「いつもこれを使っているから」という理由だけで、要件（トラフィック規模、更新頻度、チーム体制）を無視して技術を固定しない。
2. **運用者が1人しかいないのにマイクロサービス化する。** サービス間通信・デプロイパイプライン・監視の複雑さが運用能力を超える。
3. **将来の拡張を見越して不要な抽象化を先回りで入れる。** 使われる見込みの薄い設定の柔軟性やプラグイン機構を最初から作り込み、実装コストと理解コストだけが増える。
4. **認証・決済・パスワード管理を自前実装する。** セキュリティ上の欠陥を生みやすい領域は、実績のあるライブラリ・サービスに任せる。
5. **バージョンやサポート状況を確認せずに古いメジャーバージョンのまま新規プロジェクトを始める。** サポート切れが近い、またはすでに切れているバージョンを新規に採用しない。
6. **単一のデータストアで済む要件に、キャッシュ層・検索エンジン・メッセージキューなど複数のミドルウェアを最初から積み上げる。** 必要性が実証される前に構成要素を増やさない。
7. **ロックインの影響範囲を評価せずにベンダー固有機能を多用する。** 移行コストの見積もりなしに、特定サービスの独自APIに全面的に依存する設計をしない。

## バージョンについての注記

本書では特定バージョンを固定して記載していない。フレームワーク・ライブラリ・ランタイムのバージョンは頻繁に更新されるため、選定時には必ず各プロダクトの公式ドキュメントで以下を確認する。

- 現在の最新安定版（Stable / LTS）はどれか
- 選定候補のバージョンがサポート対象内か、サポート終了（EOL）が近くないか
- メジャーバージョン間の破壊的変更の有無と移行難易度

本書の推奨は「製品・技術カテゴリの選び方」を示すものであり、バージョン選定は選定時点の公式情報を優先する。
