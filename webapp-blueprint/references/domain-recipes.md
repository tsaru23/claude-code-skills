# 領域別レシピリファレンス

webapp-blueprint スキルの Phase 6（領域別レシピ適用）で参照する。Phase 1 Q1 で該当する領域がある場合のみ、その領域のセクションを適用する。該当領域がなければ読み飛ばしてよい。判断基準を表と決定木の形式でまとめる。

## 3D / インタラクティブ体験

3D表現を伴うプロダクトは、他の領域に比べて「動くところまでは作れるが、実用に耐えるパフォーマンス・アクセシビリティまで詰め切れない」失敗が多い領域である。そのため他領域より厚めに扱う。

### レンダリング: 選択肢比較

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| three.js（素） | 表現の自由度を最大化したい、Reactに依存させたくない、パフォーマンスチューニングを細かく行いたい場合 | チームがReactの宣言的な書き方に慣れており、シーングラフを手続き的に書く負荷を避けたい場合 |
| React Three Fiber + drei | Reactアプリの中に3Dシーンを統合したい、コンポーネント単位でシーンを構築したい場合 | Reactを使わないプロジェクト、three.jsの低レイヤAPIを直接叩く必要が多い場合 |
| Babylon.js | ゲームに近い複雑なシーン管理、物理演算やアニメーションエディタ等の統合ツール群を活用したい場合 | 軽量な演出のみで十分な小規模サイト（フル機能がオーバースペックになる） |
| model-viewer（Web Component） | 単一の3Dモデルを回転・ズームで見せるだけで十分な商品ビューア等 | カメラ演出やシーン内の複数オブジェクトの連動が必要な体験 |
| Spline等のノーコードツール | デザイナーが実装者を介さずに3D演出を作り込みたい、短納期でビジュアルを仕上げたい場合 | 細かいパフォーマンスチューニングやコードレベルでの最適化が必要な場合。書き出したシーンの保守性・移植性は個別に確認する |

判断の起点は「モデルを1つ見せるだけか」「複数オブジェクトが絡むシーン全体を作るか」「Reactアプリに統合するか単体で完結させるか」の3点。

### 3Dモデルの調達と生成

| 調達方法 | 特徴 |
|---|---|
| 既存アセットストア | 品質のばらつきはあるが、ライセンス条件が明記されていることが多く確認しやすい |
| 自作（Blender等） | 要件に完全に合致させられるが、モデリングスキルと制作時間が必要 |
| AIによる3D生成サービス（Tripo AI、Meshy、Luma AI等） | 短時間でたたき台を作れるが、生成物の品質・トポロジーはサービスと入力次第で大きくばらつく |

**生成物の商用利用可否とライセンスは、各サービスの利用規約を必ず確認する。** サービスによって「生成物の著作権が誰に帰属するか」「商用利用に別料金プランが必要か」「学習データに起因する権利侵害リスクをどちらが負うか」の扱いが異なり、また規約は改定されることがあるため、導入時点の最新の規約を確認する。

AI生成モデルはそのままでは実用に耐えないことが多く、次の手直しが必要になる場合がある。

- **リトポロジー**: 生成直後のメッシュは三角形数が過剰、または不均一なことが多く、リアルタイム描画向けに面数を整理する
- **UV展開**: 生成物のUVがそのままではテクスチャの継ぎ目が破綻していることがあり、貼り直しが必要になる
- **テクスチャの手直し**: 解像度不足、色味の不自然さ、法線マップの欠如などを補う

### フォーマットと最適化

| 項目 | 指針 |
|---|---|
| フォーマット | glTF/GLB を基本とする。Web向けの配信・読み込み効率に優れ、主要なライブラリが標準サポートしている |
| ジオメトリ圧縮 | Draco圧縮を適用し、頂点データのファイルサイズを削減する |
| テクスチャ圧縮 | KTX2/Basis形式を使い、GPU上で展開済みのまま扱えるようにしてメモリ使用量を抑える |
| ポリゴン数の目安 | シーン全体の合計ポリゴン数をモバイル端末での目標フレームレートから逆算する。単一の目安値を機械的に当てはめず、対象デバイスで実測して調整する |
| ドローコール | 同一マテリアルを共有するオブジェクトをまとめる、テクスチャアトラスを使うなどしてドローコール数を減らす |
| LOD（Level of Detail） | カメラからの距離に応じて表示するモデルの詳細度を切り替え、遠景の負荷を下げる |
| インスタンシング | 同一形状のオブジェクトを多数配置する場合、インスタンシング描画でドローコールを1回にまとめる |
| 最適化ツール | `gltf-transform` 等のCLIツールでDraco圧縮・テクスチャ圧縮・不要データの除去をビルドパイプラインに組み込む |

### パフォーマンス

- **デバイスピクセル比の上限設定**: `window.devicePixelRatio` をそのまま使うと高精細ディスプレイで過剰な解像度で描画してしまうため、上限（例: 2程度）をクランプする。
- **モバイルでの発熱とバッテリー**: 常時高フレームレートで描画し続けると発熱・バッテリー消費が急増するため、必要に応じてフレームレートを制限する。
- **フレームレート監視**: 開発時にフレームレートを計測し、目標値を下回るシーンを特定してから最適化対象を絞る。
- **可視範囲外での描画停止**: タブが非アクティブ、または要素がビューポート外にあるときはレンダリングループを止める。
- **アセットの遅延読み込みとプログレス表示**: 3Dアセットは容量が大きくなりやすいため、初期表示に必要な最小限のアセットのみを先に読み込み、それ以外は遅延読み込みにする。読み込み中は進捗表示を出し、体感待ち時間を減らす。

### アクセシビリティと配慮

| 項目 | 対応 |
|---|---|
| `prefers-reduced-motion` | このメディアクエリが有効な環境では、自動再生のカメラアニメーションや揺れ・回転演出を抑制、または静止画代替に切り替える |
| 3D以外の代替手段 | 3D表現がコンテンツ理解に必須にならないよう、静止画・テキストなど別経路でも情報を得られるようにする |
| WebGL非対応環境のフォールバック | WebGLが無効・非対応のブラウザや端末を検出し、静止画や簡易表示に切り替える |
| キーボード操作 | マウス・タッチ操作のみに依存させず、フォーカス移動や主要な操作をキーボードからも行えるようにする |

### リソース解放

three.js系のライブラリはガベージコレクタに任せるだけでは解放されないGPUリソースを保持するため、明示的な解放処理が必要になる。

- geometry・material・texture はそれぞれ `dispose()` を呼び出して解放する。
- コンポーネントのアンマウント時（Reactの場合は `useEffect` のクリーンアップ関数内）に、生成したシーン内のオブジェクトを走査してdisposeし、レンダラー自体も破棄する。
- 典型的なメモリリークパターン: ルート再生成のたびに古いテクスチャをdisposeせずに破棄する、イベントリスナー（`resize`等）をクリーンアップ時に解除し忘れる、アニメーションループの`requestAnimationFrame`をキャンセルせずにコンポーネントを破棄する。

### よくある失敗

1. デスクトップの開発機でのみ動作確認し、実機のモバイル端末で計測せずに公開して、低スペック端末で極端なフレームレート低下や発熱が発生する。
2. AI生成の3Dモデルをリトポロジーせずにそのまま本番投入し、ポリゴン数過多でモバイル端末が固まる。
3. コンポーネントの再マウント（ページ遷移、React Strict Modeの二重実行等）のたびにdisposeせず新規オブジェクトを生成し続け、メモリ使用量が単調増加してタブがクラッシュする。
4. `prefers-reduced-motion` を確認せず、前庭障害等のユーザーに強い映像酔いを引き起こす演出をそのまま表示する。
5. 3Dアセット一式（数十MB単位）を初期バンドルに含めてしまい、初回表示までの待ち時間が数十秒に及ぶ。

## リアルタイム/協調編集

### 選択基準

| 手段 | 向いているケース | 避けるべきケース |
|---|---|---|
| WebSocket | 双方向・低遅延の通信が継続的に必要（チャット、共同編集、リアルタイム通知） | 単純な一方向の更新通知のみで十分な場合（オーバースペック） |
| SSE (Server-Sent Events) | サーバーからクライアントへの一方向のリアルタイム通知が中心（進捗通知、フィード更新） | クライアントからの高頻度な送信も必要な場合（双方向にはWebSocketが必要） |
| ポーリング | 更新頻度が低い、リアルタイム性の要求がゆるい、インフラを単純に保ちたい場合 | 秒未満のレイテンシが求められる場合、サーバー負荷が問題になるほど高頻度に叩く必要がある場合 |
| WebRTC | ブラウザ間の直接通信（映像・音声、低遅延なP2Pデータ転送）が必要な場合 | サーバーを介した中継で十分な要件（シグナリングサーバーの構築負荷が見合わない） |

### 再接続とバックオフ

- 接続断を検知したら即座にリトライを繰り返すのではなく、指数バックオフ（再試行間隔を徐々に延ばす）を実装し、サーバー・ネットワークへの負荷集中を避ける。
- 再接続後は、断絶中に発生した更新の差分をどう補うか（欠落したイベントの再送、最新状態の全量再取得等）を設計しておく。

### 状態の競合解決

| 方式 | 特徴 |
|---|---|
| 最後の書き込み勝ち（Last Write Wins） | 実装が単純だが、同時編集時に一方の変更が無言で失われる。競合が稀、または失われても実害が小さい用途向け |
| OT（Operational Transformation） | テキスト共同編集で実績があるが、変換ロジックの実装・検証コストが高い |
| CRDT（Conflict-free Replicated Data Type） | オフライン編集や分散環境との相性がよく、マージロジックの正しさを保証しやすいが、データ構造の設計に学習コストがある |

判断の指針: 単純な状態同期（オンライン人数表示、カーソル位置共有等）ならLast Write Winsで十分なことが多い。複数人が同一ドキュメントを同時編集する要件が明確にある場合のみ、OTかCRDTの導入を検討する。自前でOTを実装するのは難度が高いため、既存のCRDTライブラリの採用を先に検討するのが定石。

### スケール時の課題

- 単一サーバープロセスでのWebSocket接続数には上限があるため、接続数が増える見込みがあるなら早期に水平スケール構成（複数インスタンス間でのメッセージブロードキャストの仕組み）を検討する。
- 複数インスタンスにまたがる状態同期には、Pub/Sub基盤や専用のリアルタイムインフラサービスの利用を検討する。

### よくある失敗

1. 再接続時のバックオフを入れず、サーバー障害時に大量クライアントが同時に再接続を試みてサーバーを再度落とす（サンダリングハード問題）。
2. 同時編集の競合解決方式を決めずに実装を進め、後から要件が発覚してデータ構造の作り直しが発生する。
3. WebSocket接続数がインスタンスあたりの上限に近づいていることに気づかず、本番でスケールした際に新規接続が拒否される。

## EC/決済

### 原則

**カード情報を自社で保持しない。** 決済代行サービス（ペイメントゲートウェイ）のトークン化・ホスティッドフォーム等を利用し、カード番号そのものが自社サーバーを経由しない構成にする。これによりPCI DSSの適用範囲（スコープ）を大幅に縮小できる。

| 項目 | 設計のポイント |
|---|---|
| PCI DSSスコープ削減 | 決済代行のiframe埋め込み型フォームやリダイレクト方式を使い、カード情報の入力・送信を自社サーバーの外側で完結させる |
| Webhookによる非同期の確定処理 | 決済の最終確定（成功・失敗）は決済代行からのWebhook通知を正とし、フロントエンドの応答だけで注文確定を判断しない |
| 冪等性 | 同じWebhookが重複配信されても注文が二重作成されないよう、決済ID等で冪等性キーを設け、処理済みかどうかを判定する |
| 在庫の同時実行制御 | 複数の注文が同時に同一在庫を確保しようとする競合を防ぐため、在庫更新にロックまたは楽観的同時実行制御（バージョン番号等）を用いる |
| 税・送料の計算責務 | 税率・送料の計算をフロントエンドの表示計算とバックエンドの確定計算で二重管理せず、確定計算はバックエンド（または決済代行・税計算サービス）に一本化する |
| 返金と部分キャンセル | 全額返金だけでなく部分返金・部分キャンセルのフローを設計し、在庫・売上集計への反映方法を決めておく |

### よくある失敗

1. フロントエンドから決済成功のコールバックを受けた時点で注文を確定させ、Webhookを実装しない。ユーザーがブラウザを閉じる、通信が切れる等でコールバックが届かないと、決済は成立しているのに注文データが作られない不整合が起きる。
2. Webhookの重複配信を考慮せず冪等性を持たせないため、決済代行側の再送によって同じ注文が二重に作成される。
3. 在庫チェックと在庫の確保処理の間にタイムラグがあり、フラッシュセール等のアクセス集中時に在庫数を超えて注文を受け付けてしまう。
4. カード情報をログに出力してしまう（デバッグログにリクエストボディ全体を出力する実装で発生しやすい）。
5. 税・送料の計算をフロントエンドのJavaScriptのみで行い、APIリクエストを改変されると実際の請求額と表示額がずれる。

## メディア/CMS

### 比較

| 選択肢 | 向いているケース | 避けるべきケース |
|---|---|---|
| ヘッドレスCMS | 非エンジニアの編集者が頻繁に更新する、プレビュー・公開予約等の編集機能が必要な場合 | 更新頻度が極めて低い、コンテンツをコードと一緒にバージョン管理したい場合 |
| ファイルベース（MDX等） | 開発者自身がコンテンツを書く、Gitでの差分管理・レビューを活かしたい場合 | 非エンジニアの編集者が日常的に更新する必要がある場合 |
| 自前DB | CMSの標準機能では表現しにくい独自のコンテンツ構造・検索要件がある場合 | 一般的な記事・ページ管理で十分な場合（車輪の再発明になりやすい） |

### 設計上の注意

- **プレビュー機能**: 下書き状態のコンテンツを公開前に確認できる仕組み（プレビュートークン付きURL等）を用意し、公開ボタンを押す前に見た目を検証できるようにする。
- **公開予約**: 指定日時に自動公開する機能が必要な場合、CMS側の予約機能の有無と、予約が失敗した場合の検知手段を確認する。
- **画像の配信最適化**: 画像CDNやフレームワーク組み込みの画像最適化機能を使い、フォーマット変換（WebP/AVIF等）とレスポンシブなサイズ配信を行う。
- **編集者の権限設計**: 「下書き作成のみ」「公開権限あり」「全体管理者」等、役割に応じた権限を分け、公開権限を必要最小限のメンバーに絞る。

### よくある失敗

1. プレビュー機能を用意せず、編集者が「公開してから見た目を確認する」運用になり、誤字脱字やレイアウト崩れが本番環境で発覚する。
2. 全編集者に管理者権限を付与してしまい、意図しない設定変更や誤削除が起きたときに原因の特定が難しくなる。
3. 画像を最適化せずオリジナルサイズのまま配信し、記事ページの表示速度が大きく低下する。

## AI機能の組み込み

### 設計のポイント

| 項目 | 指針 |
|---|---|
| LLM API呼び出しの設計 | 必ずサーバー経由で呼び出し、APIキーをクライアント（ブラウザ・モバイルアプリ）に露出させない |
| ストリーミング応答 | 生成に時間がかかる場合、逐次的にトークンを返すストリーミング応答でユーザーの体感待ち時間を減らす |
| プロンプトインジェクション対策 | ユーザー入力や外部コンテンツ（Webページ、ドキュメント等）をプロンプトに含める場合、それらが指示として解釈されるリスクを考慮し、システム指示とユーザー入力を明確に分離する。信頼できない入力に基づいて権限を要する操作（送金、削除等）を自動実行しない |
| レート制限とコスト上限 | ユーザー単位・IP単位でのリクエスト回数制限を設け、想定外の高頻度呼び出しによるコスト急増を防ぐ。月次のコスト上限アラートも合わせて設定する |
| 出力の検証 | LLMの出力をそのまま実行・表示するのではなく、期待する形式（JSON等）になっているかの検証や、有害な内容のフィルタリングを挟む |
| AI利用の明示 | 生成されたコンテンツやAIとのやり取りであることをユーザーに明示し、誤認を防ぐ |
| ログとプライバシー | プロンプトや応答をログに保存する場合、個人情報や機微情報が含まれる可能性を踏まえ、保存期間・アクセス権限を設計する |

### よくある失敗

1. クライアントサイドのコードに直接APIキーを埋め込み、ブラウザの開発者ツールから容易に窃取される状態で公開する。
2. レート制限を設けず、悪意あるユーザーや誤動作するクライアントからの連続リクエストで想定外に高額なAPI利用料が発生する。
3. 外部から取得したテキスト（Webページのスクレイピング結果、ユーザーがアップロードしたドキュメント等）をそのままプロンプトに連結し、埋め込まれた指示文に従って意図しない挙動を起こす。
4. LLMの出力を検証せずにそのままデータベースへの書き込みや外部API呼び出しのパラメータとして使用し、不正な形式や意図しない値が実行される。

## フォーム/問い合わせ

### 設計のポイント

| 項目 | 指針 |
|---|---|
| スパム対策 | honeypot（人間には見えず、ボットだけが埋めてしまう隠しフィールド）を設置する。加えてサーバー側でのレート制限を組み合わせる。CAPTCHAは、上記対策だけでは不十分な場合の追加手段として位置づけ、正規ユーザーの離脱要因になりうる点も考慮する |
| 送信の冪等性 | 二重クリックや通信再送によって同じ問い合わせが複数件登録されないよう、送信ボタンの多重送信防止やリクエスト側の冪等性キーを用意する |
| メール送信の到達性 | 問い合わせ通知や自動返信メールがスパム判定されないよう、送信ドメインにSPF・DKIM・DMARCを設定する |
| 入力内容の保持 | 送信エラーやバリデーション失敗時に、ユーザーが入力した内容を保持し、再入力の手間をなくす |

### よくある失敗

1. スパム対策を一切入れずに公開し、ボットによる大量の自動送信で問い合わせ対応が埋もれる。
2. 送信ボタンの二重クリック対策をせず、同一内容の問い合わせが複数件登録される。
3. 送信ドメインにSPF/DKIM/DMARCを設定せず、自動返信メールが相手先でスパムフォルダに振り分けられ、ユーザーに気づかれない。
4. バリデーションエラー時に入力内容が消え、長文の問い合わせをユーザーが最初から書き直すことになり離脱する。

## 多言語対応

### 設計のポイント

| 項目 | 選択肢と指針 |
|---|---|
| URL設計 | サブパス（`/ja/`、`/en/`）、サブドメイン（`ja.example.com`）、ドメイン分割（`example.jp`、`example.com`）のいずれかを選ぶ。運用体制が小さいうちはサブパス方式が構成・証明書管理・SEO評価の統合の面で扱いやすい |
| 翻訳リソースの管理 | 言語ごとのキー・バリュー形式のリソースファイルで管理し、翻訳漏れを検知する仕組み（未翻訳キーのフォールバック表示、CIでの欠落チェック等）を用意する |
| 日付・数値・通貨のロケール | 標準の国際化APIやライブラリを使ってロケールごとのフォーマットを適用し、独自の文字列結合で書式を組み立てない |
| RTL（右から左に読む言語） | アラビア語・ヘブライ語等に対応する場合、レイアウトの左右反転（論理プロパティの使用等）を早い段階で考慮する。後から追加すると全体のCSS見直しが必要になりやすい |
| hreflang | 同一コンテンツの言語別ページ間を`hreflang`で相互に関連付け、検索エンジンに適切な言語版を認識させる |

### よくある失敗

1. URL設計を後から変更し、既存ページのSEO評価やブックマークされたリンクが失われる。
2. 翻訳リソースの欠落チェックをCIに組み込まず、未翻訳のキー文字列がそのまま本番画面に表示される。
3. 日付や数値を文字列結合で自前フォーマットし、言語によって桁区切りや日付順序（月日年/日月年）が崩れる。
4. RTL対応を後回しにした結果、左右固定のマージン・アイコン配置等がRTL言語で軒並み反転が必要になり、大規模な手戻りが発生する。
5. hreflangを設定せず、検索結果に意図しない言語のページが表示され、ユーザーが離脱する。
